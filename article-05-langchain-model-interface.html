LangChain enters the series here. Everything from the last three articles was building toward this moment on purpose: you've now felt, with your own hands, exactly what LangChain's model interface exists to fix. Three SDKs. Three different places for a system instruction. Three different response shapes, one of them a list of content blocks with a thinking block in front. Sampling knobs that don't agree on their ranges, or even on whether a given model accepts them. Watch what happens to all of that in this article, and, just as usefully, which parts of Article 4's lessons a framework can't make disappear.

Setup

LangChain's architecture, previewed back in Article 1, is concrete now instead of abstract: langchain-core holds the shared abstractions, and each provider gets its own thin integration package.

terminal
pip install langchain langchain-openai langchain-anthropic langchain-google-genai

Four packages: langchain itself, plus one integration package per provider you want to talk to. Your .env file doesn't change at all, keep the same OPENAI_API_KEY, ANTHROPIC_API_KEY, and GOOGLE_API_KEY from Articles 2 and 3. Each integration package reads its provider's key from the environment automatically, exactly like the raw SDKs did.

Your first LangChain call

python
import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage

load_dotenv()
model = ChatOpenAI(model="gpt-5.5")

messages = [
    SystemMessage(content="You are a concise, helpful assistant."),
    HumanMessage(content="Explain what an API is in two sentences."),
]

response = model.invoke(messages)
print(response.text)

Line by line: what's familiar, what's new

  • ChatOpenAI(model="gpt-5.5") builds the model object. No explicit API key here at all; it's read from OPENAI_API_KEY automatically, the same environment variable you've had in your .env since Article 2.
  • SystemMessage and HumanMessage come from langchain_core.messages, LangChain's own message classes. They replace the {"role": ..., "content": ...} dicts you built by hand in every earlier article. Functionally they carry the same information; structurally they're real Python objects instead of raw dicts, which matters once you start passing messages through chains later in this series.
  • model.invoke(messages) is the call. One method name, invoke, regardless of which provider is underneath, replacing chat.completions.create, messages.create, and generate_content from the last two articles.
  • response.text gets you the reply as a plain string. One consistent path, replacing response.choices[0].message.content, Article 2's filtering of Claude's text blocks, and Gemini's response.text. The object invoke returns is an AIMessage, and it also has a .content attribute, but reach for .text out of habit: the next section shows why.

That's the whole payoff of the last three articles, made visible in four lines.

Fig. 1 — Three raw call shapes from Articles 2 and 3 collapse into one calling pattern once a provider sits behind LangChain's interface.

Now swap the provider

This is the part worth actually running, not just reading. Change two lines, keep everything else identical:

python
from langchain_anthropic import ChatAnthropic

model = ChatAnthropic(model="claude-sonnet-5")

response = model.invoke(messages)
print(response.text)

Same messages list, unchanged, SystemMessage included. Same .invoke(messages) call. Same .text access. Recall from Article 2 that Anthropic's raw SDK doesn't even accept a system-role message in its messages list at all, it has to be a separate top-level argument. LangChain's ChatAnthropic class absorbs that translation internally: hand it a SystemMessage and it does the right thing for Anthropic's actual API underneath. It also fills in Anthropic's required max_tokens for you (it defaults to the model's maximum output), which is why there isn't one here.

Here's why .text rather than .content. Recall Article 2's discovery that claude-sonnet-5 thinks by default and returns its reasoning as a thinking block ahead of the answer. LangChain doesn't hide that: for this call, response.content is a list of content blocks, [{"type": "thinking", ...}, {"type": "text", "text": "..."}], not a string, so print(response.content) would print the whole list, reasoning included. response.text walks those blocks and returns just the answer text, which is exactly the filtering you wrote by hand in Article 2, now done for you.

Gemini, same story again:

python
from langchain_google_genai import ChatGoogleGenerativeAI

model = ChatGoogleGenerativeAI(model="gemini-3.8-flash")

response = model.invoke(messages)
print(response.text)

Recall Article 3: Gemini's raw SDK wanted contents instead of messages, "model" instead of "assistant" as the role name, and text wrapped in a "parts" list. None of that surfaces here. Same messages, same call, same .text. Gemini is a second reason to prefer .text, too: with Gemini 3 models, response.content typically comes back as a list of blocks as well, because LangChain keeps the reply's thought signature from Article 3 attached to the text block so it can be sent back on the next turn.

Three providers, one interface. This is genuinely what "LangChain solves the provider-switching problem" means in practice, not marketing language: it's the exact same calling code, with only the constructor swapped.

Why this actually works: one shared base class

This isn't three separate implementations that happen to look similar. ChatOpenAI, ChatAnthropic, and ChatGoogleGenerativeAI all inherit from the same class, BaseChatModel, defined once in langchain-core. .invoke() and .stream() are defined on that shared base, with the same method signature and the same AIMessage return type, and each provider's integration package is responsible only for translating LangChain's message objects into whatever shape that provider's actual API wants, then translating the response back. That's the whole architecture. It's not magic, it's an adapter pattern, applied consistently across every provider LangChain supports.

Fig. 2 — Not three separate implementations that happen to look similar: three real subclasses of one shared base, an adapter pattern applied consistently.

Streaming

Streaming follows the same unification:

python
for chunk in model.stream(messages):
    print(chunk.text, end="", flush=True)

.stream() yields AIMessageChunk objects instead of one AIMessage, each with the same .text you already know, containing just that chunk's fragment of the answer. Same method name, same attribute, regardless of provider. And the .content-versus-.text point matters even more here: with Claude, some chunks carry thinking deltas rather than answer text, so print(chunk.content) would sprinkle raw reasoning dicts into your output, while chunk.text is simply empty for those chunks. Compare that to Article 2's chunk.choices[0].delta.content versus Article 3's chunk.text, and this is the difference a unified interface actually buys you: one pattern, memorized once.

init_chat_model: one function, any provider

There's an even more compact entry point worth knowing, useful when the provider itself is something you want to decide at runtime rather than hardcode as an import:

python
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5.5")
# or
model = init_chat_model("anthropic:claude-sonnet-5")
# or
model = init_chat_model("google_genai:gemini-3.8-flash")

response = model.invoke(messages)

init_chat_model takes a single "provider:model-name" string, figures out which integration package to use, and hands you back the right class already constructed, a ChatOpenAI, ChatAnthropic, or ChatGoogleGenerativeAI under the hood, indistinguishable from building it directly. It's a small function, but it's the cleanest expression of what this whole article has been demonstrating: from here on, the provider is a string, not a different code path.

Where the unification stops

Worth being precise, in the same spirit as Article 3's honesty about what LiteLLM doesn't solve: LangChain's unification is real at the level you've just seen, invoke, stream, message objects, .text, and it now reaches further into constructor arguments than you might expect. The three classes store settings under provider-flavored field names underneath (ChatOpenAI keeps the model in model_name, ChatGoogleGenerativeAI keeps the output cap in max_output_tokens), but each accepts the common spellings as aliases, so model=, max_tokens=, and either stop= or stop_sequences= all work on all three classes and get translated into each API's own parameter.

What LangChain can't unify is what a given model will actually accept, which is Article 4's whole lesson, and it surfaces through the wrapper in three different ways:

  • Passed through and refused. init_chat_model("openai:gpt-5.5", stop=["DONE"]) constructs happily, and then the call fails with the same Unsupported parameter: 'stop' 400 error from Article 4. LangChain translated the name correctly; the model still says no.
  • Silently dropped. ChatOpenAI knows that gpt-5.5 only accepts temperature=1 while it's reasoning, so it quietly drops any other value rather than erroring. Set temperature=0.2 on ChatOpenAI(model="gpt-5.5") and it simply has no effect; add reasoning_effort="none" and the temperature is sent again.
  • Sent and rejected. ChatAnthropic makes no such allowance: ChatAnthropic(model="claude-sonnet-5", temperature=0.3) sends the temperature, and every call fails with Article 4's 400 error.

Three integrations, three different behaviors for the same kind of mistake. That's not a knock on LangChain so much as a reminder of what it is: a translation layer passing your intent to real APIs that each have their own opinion.

A related check worth running on the parameter Article 4 covered directly, the reasoning-effort knobs: ChatOpenAI, ChatAnthropic, and ChatGoogleGenerativeAI all expose a reasoning_effort field, a genuine, if partial, unification over the three different shapes Article 4 walked through (OpenAI's own reasoning_effort string, Anthropic's output_config={"effort": ...}, Gemini's thinking_level). Each class translates it into its provider's real parameter: on ChatAnthropic, for example, reasoning_effort="low" becomes output_config={"effort": "low"} with adaptive thinking switched on. But the values accepted underneath that shared name still don't match: constructing ChatAnthropic(reasoning_effort=...) only accepts "low", "medium", "high", "xhigh", or "max", confirmed by actually passing "minimal" and watching it reject with a validation error, while ChatGoogleGenerativeAI's version only accepts "minimal", "low", "medium", or "high", an overlapping but genuinely different set, and even that passes validation without guaranteeing the model supports it: per Article 4, gemini-3.8-flash itself only offers "low", "medium", and "high". The one value all three classes and all three default models agree on is "low". Same lesson as the temperature story above, one level up: a shared field name is real progress over three unrelated ones, but it's not the same thing as a shared contract, check the actual accepted values before assuming they line up.

Setting up the project

Starting here, every remaining article in this series builds one continuous project: an AI assistant for Tidewave, a fictional project-management and team-collaboration SaaS product with a standard subscription plan. Over the rest of the series, this assistant grows from the plain single-turn call you just wrote into something that remembers conversations, answers questions by retrieving Tidewave's actual documentation, checks things like a customer's subscription status through a tool, and finally acts as a proper agent deciding for itself when to search docs versus when to use a tool.

The first piece of that project's actual code is small, worth writing now: a single function the rest of the series will reuse rather than re-importing a specific provider class in every article.

python
from langchain.chat_models import init_chat_model
from langchain_core.language_models.chat_models import BaseChatModel


def get_model(
    provider_and_model: str = "anthropic:claude-sonnet-5", **kwargs
) -> BaseChatModel:
    """Return a configured chat model for Tidewave's assistant.

    Accepts an init_chat_model-style "provider:model-name" string, so
    swapping the underlying provider anywhere in the project later is a
    one-argument change, not a rewrite. Any extra settings, such as
    reasoning_effort="low", are passed straight through.
    """
    return init_chat_model(provider_and_model, **kwargs)

Notice what's deliberately not here: a temperature. The classic instinct for a support assistant is a low temperature, since most of what it'll do (from Article 9 onward) is answer questions accurately from documentation, not write creatively. But the previous section just showed what that instinct does on each provider's current default model: a hard 400 error on claude-sonnet-5, a silently ignored value on gpt-5.5, and a setting Google advises against on gemini-3.8-flash. So get_model() leaves sampling alone and lets each model use its tuned defaults, and accuracy comes from where it actually comes from on these models: clear instructions in the prompt, which Anthropic itself recommends in place of sampling parameters, and grounding answers in retrieved documentation later in the series. When a particular step does want to trade depth for speed, get_model(reasoning_effort="low") is the portable dial, since "low" is the value all three classes accept.

Every later article's hands-on code will call get_model() rather than constructing a provider class directly, which means the entire rest of this series' project code is, from this point forward, provider-agnostic by construction, and correctly configured by default.
