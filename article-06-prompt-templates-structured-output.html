This one solves two problems that show up the moment you try to build something real on top of that: prompts that are just hardcoded strings don't scale past a demo, and a model's reply is free text, which is a bad fit for code that needs an actual answer, not a paragraph to parse.

Why a hardcoded string stops working

Every prompt you've written so far in this series has been a literal string sitting inside a HumanMessage. That's fine for a one-off example. It stops being fine the moment the same prompt needs to run with different inputs, which is every real application: a support assistant answering different questions, a summarizer given different documents, a classifier looking at different messages. You end up either duplicating near-identical strings everywhere or hand-rolling f-string interpolation and hoping you never forget to escape something. Neither scales, and neither separates "the prompt" from "the code," which matters once a prompt is something you're iterating on independently of your application logic.

ChatPromptTemplate

LangChain's answer is a template object: write the prompt once, with placeholders, and fill it in with different values on each call.

python
from langchain_core.prompts import ChatPromptTemplate

template = ChatPromptTemplate.from_messages([
    ("system", "You are a concise, helpful assistant for {product}."),
    ("human", "{question}"),
])

prompt_value = template.invoke({
    "product": "Tidewave",
    "question": "What plans do you offer?",
})

print(prompt_value.to_messages())

What's happening here

  • from_messages([...]) takes a list of (role, template_string) tuples, one per turn, and builds a reusable template object. {product} and {question} are placeholders, filled in later.
  • template.invoke({...}) fills those placeholders in, using a dict keyed by variable name. This is the same .invoke() method name you already know from model.invoke(), doing conceptually the same thing: take an input, produce an output.
  • The result is a ChatPromptValue, not a plain string or a list. .to_messages() turns it into the real SystemMessage/HumanMessage objects from Article 5, ready to hand to a model.
Fig. 1 — A template fills its placeholders into real message objects, which pass straight into a model's invoke() unchanged.

That last step, the conversion, is actually optional. model.invoke() accepts a ChatPromptValue directly:

python
from models import get_model  # Article 5's helper, saved in your project as models.py

model = get_model()
response = model.invoke(prompt_value)
print(response.text)

No .to_messages() needed. The prompt value and the message list are interchangeable as far as .invoke() is concerned, so you can skip the conversion step in most code.

get_model() is Article 5's project helper, reused here for the first time exactly as intended: no init_chat_model import, no hardcoded provider string, just the same function every later article in this series calls. And the reply is read with .text, not .content, for the reason Article 5 gave: with Claude's default thinking on, .content is a list of content blocks, and .text is always just the answer.

MessagesPlaceholder: room for a variable-length history

Templates aren't limited to fixed slots. MessagesPlaceholder reserves a spot for a whole list of messages, whatever that list happens to contain at call time:

python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.messages import HumanMessage, AIMessage

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant for {product}."),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])

prompt_value = template.invoke({
    "product": "Tidewave",
    "history": [
        HumanMessage(content="Hi"),
        AIMessage(content="Hello! How can I help?"),
    ],
    "question": "What plans do you offer?",
})

"history" here isn't a string to interpolate, it's a variable that must resolve to a list of message objects, spliced into the conversation at that exact position. This is worth remembering specifically: it's the actual mechanism Article 8's memory system will use to inject prior conversation turns into a prompt. Nothing new to learn there when you get to it, just this same placeholder, filled with a growing list instead of a hardcoded one.

Getting reliable structured output

Here's a problem you'll hit constantly: you don't want a paragraph back, you want data. Say you're building the piece of Tidewave's assistant that triages an incoming support message, you want a category, a priority level, and a short summary, as actual fields your code can branch on, not three sentences you have to regex apart.

The naive fix is asking nicely: "Please respond in JSON with fields category, priority, and summary." This works often enough to feel reliable and fails often enough to break production: the model wraps the JSON in a markdown code fence, adds a sentence before it, uses "priority": "High" when your code expects lowercase, or just drifts from the schema entirely on a longer conversation. None of that is a hypothetical; it's the standard failure mode of prompting for structure instead of enforcing it.

Fig. 2 — Same request, completely different failure surface: one is prompting and hoping, the other is the model's native structured output, constrained to the schema.

with_structured_output

LangChain's fix doesn't prompt harder, it uses the model's own native structured-output support, the same underlying mechanism a framework-free implementation would reach for, wired up for you. All three providers in this series now offer it: you hand the API a JSON schema, and the model's output is constrained to match it, rather than merely asked to.

python
from typing import Literal
from pydantic import BaseModel, Field

class TicketClassification(BaseModel):
    """Structured classification of a Tidewave support message."""
    category: Literal["billing", "technical", "feature_request", "other"] = Field(
        description="The best-fit category for this support message"
    )
    priority: Literal["low", "medium", "high"] = Field(
        description="How urgently this message needs a response"
    )
    summary: str = Field(description="One-sentence summary of the issue")


model = get_model()
classifier = model.with_structured_output(
    TicketClassification, method="json_schema"
)

result = classifier.invoke("My card was charged twice this month and I need a refund ASAP.")

print(result.category)  # "billing"
print(result.priority)  # "high"
print(type(result))     # <class '__main__.TicketClassification'>

Walking through the pieces

  • The TicketClassification class is a Pydantic model, not a LangChain-specific construct. Pydantic is a third-party library, not something built into Python itself, but it's the de facto standard across the Python ecosystem for exactly this: define a class with typed fields, and it validates that any data assigned to it actually matches those types. It arrives automatically as a dependency when you install LangChain, so there's nothing extra to install here.
  • Each field's type constrains what's valid. Literal["billing", "technical", "feature_request", "other"] restricts category to exactly those four strings and nothing else, which matters specifically because it's the difference between a classifier with four reliable buckets and one that occasionally invents a fifth category on its own. Each Field(description=...) tells the model what that field actually means; this description is genuinely sent to the model, it's not just a code comment.
  • model.with_structured_output(TicketClassification, method="json_schema") doesn't return a chat model anymore, it returns something new: call .invoke() on it and you get back an instance of TicketClassification directly, not an AIMessage. The parsing already happened.
  • method="json_schema" picks the mechanism: the provider's native structured-output feature, which for Claude is Anthropic's output_config JSON-schema format, for OpenAI a json_schema response format, and for Gemini a JSON response schema. OpenAI's and Gemini's classes already default to this; ChatAnthropic still defaults to an older technique, forcing the model to call a "tool" whose arguments match the schema. That works on claude-sonnet-5, but Anthropic's newest top models, Claude Opus 5.5 and Fable 5.1, reject forced tool use outright, and LangChain then falls back to an unforced call that raises an error if the model decides not to use the tool. Passing method="json_schema" explicitly gives you the same mechanism on every provider and every current Claude model, and structured outputs work alongside Claude's thinking, which stays out of the constrained answer.
  • Nothing here is provider-specific. with_structured_output is defined once on BaseChatModel, exactly like invoke and stream from Article 5, so the same lines work regardless of what get_model() actually hands back, Claude by default, or get_model("openai:gpt-5.5") if you override it. The unified-interface story from the last article extends to structured output too, not just plain text.

A brief note on the old way, in case you see it in other material: PydanticOutputParser, combined with format instructions stuffed into the prompt telling the model how to shape its JSON, still exists and still works. It's the technique that predates most providers offering real structured-output support natively. with_structured_output is the better default now that native structured output is available everywhere this series cares about; reach for the older parser only if you're stuck on a model or provider that genuinely doesn't support structured output at all.

Putting both together

The realistic version combines a template with structured output, since real inputs come from somewhere other than a hardcoded string:

python
template = ChatPromptTemplate.from_messages([
    ("system", "You classify incoming support messages for {product}."),
    ("human", "{message}"),
])

prompt_value = template.invoke({
    "product": "Tidewave",
    "message": "My card was charged twice this month and I need a refund ASAP.",
})

result = classifier.invoke(prompt_value)
print(result.summary)

Template formats the prompt, classifier (the structured-output-wrapped model from a moment ago) turns the reply straight into a TicketClassification object. Two separate, composable pieces, each doing one job.

What's next

Notice the shape of that last example: format a prompt, then separately call .invoke() on something else with the result. That's a completely reasonable way to write it, and it's also exactly the pattern LCEL exists to make more natural.
