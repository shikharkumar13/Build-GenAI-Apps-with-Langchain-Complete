Tidewave's assistant can now retrieve, remember, and act, and Article 13 ended on the one real gap left, you can't see what actually happened inside a run. This article closes it, the last new concept this series covers before Article 15 pulls everything together into one finished build.

Why this matters more now than it would have in Article 5

A single model.invoke() call is easy to debug: read the prompt, read the response, done. An agent loop from Article 13 isn't: a question comes in, the model might call zero, one, or several tools, each with its own inputs and outputs, before producing a final answer, and the whole sequence happens inside one agent.invoke() call with no visibility into the steps by default. When an answer comes back wrong, "wrong" could mean bad retrieval, a tool called with the wrong arguments, a prompt that didn't include what you thought it did, or the model itself reasoning badly, and reading source code doesn't tell you which. That's what observability is for: seeing the actual steps a specific run took, not just the code that could produce them.

What can and can't be run without an account

Every other article in this series ran real code, sometimes against a stand-in model, sometimes fully locally with genuine computed output. This one needs a caveat: LangSmith is a hosted product, not a local library. Traces are uploaded to LangSmith's servers and viewed in its web app at smith.langchain.com, which needs an account and an API key, so there are no screenshots of that app here. What can run locally is everything on your side of the upload: the setup, the @traceable decorator, and the trace itself. The run trees shown below are real, captured by intercepting LangSmith's client just before it would have uploaded them, so they're exactly what the web app would receive.

Setup

terminal
pip install langsmith
.env
# .env
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...
LANGSMITH_PROJECT=tidewave-assistant

The .env file isn't read on its own, so load it first thing, before any model or chain runs, the same load_dotenv() call from Article 3:

python
from dotenv import load_dotenv

load_dotenv()

Two more variables you may need: an EU-region account sends traces to a different server, so add LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com (no trailing slash), and an API key that belongs to several workspaces needs LANGSMITH_WORKSPACE_ID to say which one.

Worth flagging directly, in the same spirit as this series' other naming-migration catches: a lot of material you'll find still shows LANGCHAIN_TRACING_V2, LANGCHAIN_API_KEY, and LANGCHAIN_PROJECT instead. Both sets of names work, confirmed by reading the actual installed package's environment-lookup code, it checks the LANGSMITH_ prefix first and falls back to LANGCHAIN_ only if that's unset (an empty value counts as unset). LANGSMITH_ is the current name; LANGCHAIN_ is legacy compatibility, not a wrong answer, just worth knowing which one you're looking at.

No code changes needed, and here's why

Set those three variables and every chain, retriever, tool, and agent from this entire series starts getting traced automatically, without touching a single line of Tidewave's actual code. This isn't a special integration LangSmith bolted onto specific classes; it's a direct consequence of the same fact Article 7 built this whole series around: everything is a Runnable, and every Runnable shares one callback system. LangSmith's tracer is a callback handler, and whenever a Runnable starts a run, LangChain's callback manager checks whether tracing is enabled and attaches that handler automatically, so it sees every .invoke() call, every step of every chain, every tool execution inside an agent loop (a create_agent graph is a Runnable too), the same way .batch() and .stream() worked identically everywhere back in Article 7 for the same underlying reason.

What a trace actually shows

For a single model.invoke() call: the exact messages sent, the exact response, latency, token usage, and the model name and settings used, the same numbers Article 2's response.usage printed and the parameters Article 4 tuned, now attached to one real, specific call.

For something with real structure, Article 11's RAG chain or Article 13's agent, a trace is a full call tree. Here's the tree Article 13's agent, FakeAgentModel stand-in and all, actually produces for one agent.invoke(), captured locally with tracing enabled:

output
LangGraph [chain]
  model [chain]
    FakeAgentModel [llm]
  tools [chain]
    check_subscription_status [tool]
  model [chain]
    FakeAgentModel [llm]

Each line is one run, and the bracketed part is its run type, which is how the web app decides what to show for it. The root is the whole agent.invoke(). Under it, the agent's graph steps, called model and tools, appear in the order they ran: a model call that requested the tool, the tool executing with its actual arguments and return value, then a second model call that wrote the answer. Each [llm] run holds the full message list that call received, system prompt included. The root is named LangGraph by default; pass name="tidewave_assistant" to create_agent and the root carries that name instead, which helps once one project holds traces from several agents. It's precisely the sequence of HumanMessage, AIMessage with tool_calls, ToolMessage, final AIMessage that Article 13's FakeAgentModel example printed to the console by hand, except in LangSmith it's a real trace of a real run, browsable and shareable, not something you had to construct a stand-in model to see.

Fig. 2 — What Article 13's FakeAgentModel printed by hand to prove the loop worked, a real trace shows for any real run, browsable after the fact.

Tracing your own code with @traceable

Everything above is automatic because it's all built from Runnables. Plain Python functions that aren't, some cleanup logic sitting inside one of Tidewave's tools, say, need one line to show up in the same trace tree:

python
from langsmith import traceable
from langchain_core.tools import tool

@traceable
def normalize_email(email: str) -> str:
    return email.strip().lower()

@tool
def check_subscription_status(customer_email: str) -> str:
    """Check a Tidewave customer's current subscription plan and billing status."""
    fake_db = {
        "sam@example.com": "Team plan, active, next billing date 2026-09-15",
        "priya@example.com": "Starter plan, active",
    }
    return fake_db.get(normalize_email(customer_email), "No account found for that email.")

That's Article 12's tool with one helper added. Rebuild Article 13's agent with this version and the captured tree gains one line, nested exactly where the call happened:

output
LangGraph [chain]
  model [chain]
    FakeAgentModel [llm]
  tools [chain]
    check_subscription_status [tool]
      normalize_email [chain]
  model [chain]
    FakeAgentModel [llm]

@traceable defaults to the chain run type; @traceable(run_type="tool") or name="..." change how it's labeled. It also works with no LangChain involved at all: decorate plain functions, or wrap a raw SDK client with wrap_openai or wrap_anthropic from langsmith.wrappers, and Article 2's direct SDK calls get traced the same way.

Worth knowing directly: this fails safe. Verified by running a @traceable function with tracing enabled and the endpoint pointed at a server that doesn't exist: the function returned its real result, and the only sign of trouble was a warning logged by the failed background upload. A tracing outage or a bad API key doesn't take your application down with it.

Production note

Two practical details follow from that background upload. Traces are sent from a background thread and flushed when the process exits normally, which covers scripts and long-running servers; in a serverless function that can be frozen as soon as it returns, call wait_for_all_tracers() from langchain_core.tracers.langchain before returning, or recent traces can be lost. And a trace holds everything the run saw, so Tidewave's traces contain customer emails and account details. Setting LANGSMITH_HIDE_INPUTS=true and LANGSMITH_HIDE_OUTPUTS=true keeps inputs and outputs out of traces entirely, and @traceable(process_inputs=...) or create_anonymizer from langsmith.anonymizer redacts selectively instead.

Evaluation, briefly

LangSmith does more than tracing, most notably evaluation: running a set of test inputs against your chain or agent and checking the outputs against expected results, useful for catching a regression the moment a prompt or model swap changes behavior somewhere you didn't expect. Worth knowing exists once Tidewave's assistant is something other people depend on; day to day, tracing is what you'll actually reach for, which is why it's what this article spent its time on.
