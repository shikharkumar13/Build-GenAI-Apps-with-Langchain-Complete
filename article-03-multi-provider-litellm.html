Two providers down. By the end of Article 2 you'd already hit four real differences between OpenAI and Anthropic: where the system instruction lives, whether an output cap is required, what the method is called, and how the reply is unwrapped from the response, with Claude's thinking block sometimes sitting in front of it. Two providers, four inconsistencies. This article adds a third provider, Google's Gemini, watches the inconsistency count grow again, and then shows you the tool many working AI engineers reach for once that pattern gets old: LiteLLM, a single interface that sits in front of upwards of a hundred providers.

What's distinctive about Gemini

Google's Gemini models stand out for two things worth knowing before you touch any code. They're natively multimodal, taking text, images, audio, and video as input to the same model, and they can ground answers in live Google Search results when you want that. Gemini also helped make very large context windows normal: Google shipped million-token windows back in 2024, including on its cheap Flash tier, when that was still a premium feature elsewhere. Today the mainstream models from all three providers in this series accept around a million tokens, so long context on its own is no longer a Gemini-specific reason to pick it.

None of that changes the fundamentals from Article 2. It's still a chat-style API, still role-based messages under the hood. What's different is the SDK and a few conventions, which is exactly what the rest of this article walks through.

A quick warning about which package to install

If you search for "Gemini Python SDK" you will find plenty of tutorials, including older versions of Google's own docs, pointing at a package called google-generativeai. That package is legacy: Google replaced it with a new, unified SDK called google-genai, and support for the old one ended entirely on November 30, 2025. This is worth calling out explicitly because it's a very easy trap: the old package still installs from PyPI, so nothing stops you from quietly building on an unsupported foundation.

terminal
pip install google-genai

Use google-genai. If you see import google.generativeai as genai in something you're reading, treat it as a signal the material predates the migration.

Your first Gemini call

python
import os
from dotenv import load_dotenv
from google import genai

load_dotenv()
client = genai.Client(api_key=os.getenv("GOOGLE_API_KEY"))

response = client.models.generate_content(
    model="gemini-3.8-flash",
    contents="Explain what an API is in two sentences.",
)

print(response.text)

What's different from OpenAI and Anthropic

  • from google import genai is the import; the installed package is google-genai, but the importable module is google.genai, accessed here via the shorter from google import genai form.
  • genai.Client(api_key=...) builds the client, same pattern as before. Google's current docs name the environment variable GEMINI_API_KEY, but the SDK accepts GOOGLE_API_KEY too, and uses GOOGLE_API_KEY if both are set. This series standardizes on GOOGLE_API_KEY, because LiteLLM (later in this article) and LangChain's Gemini integration (Article 5) both check that name first as well, so one line in your .env covers all three.
  • client.models.generate_content(...) is the call. Notice there's no .chat or .messages in the path: Gemini's SDK organizes this differently, everything hangs off client.models.
  • contents replaces messages. For a single-turn question like this one, you can just pass a plain string, no role-tagged dict required. That's a genuine simplification for the simple case, though multi-turn conversations still need a structured list, which the conversation-loop version below shows.
  • response.text is a convenience property that hands you the reply as a plain string directly, no .choices[0] indexing and no filtering through content blocks the way Article 2 had to for Claude. Gemini's current models also think before answering by default, but .text contains only the final answer, never the internal reasoning. Under the hood there's still a more detailed structure (candidates, parts, safety ratings), but for the common case, .text is genuinely the whole answer.
  • One thing you'll probably see the first time you run this: a one-off warning in your terminal saying "Direct use of automatic function calling (AFC) in Models.generate_content is not recommended." It's harmless. The SDK logs it once per run whether or not you're using tools, and automatic function calling is a tools feature this article doesn't touch (tools get their own article, Article 12). Your reply still prints right after it.

On model choice: gemini-3.8-flash is Google's current stable Flash model as of September 2026, described in Google's docs as its most intelligent Flash model yet. Flash-Lite variants such as gemini-3.5-flash-lite sit below it as the cheapest, fastest tier, and a Pro tier, currently in preview as gemini-3.1-pro-preview, is aimed at the most complex problems. Same caveat as Article 2: the names move fast, the tier structure doesn't.

One more parallel with Article 2. Just as OpenAI now recommends its newer Responses API over Chat Completions, Google now recommends a newer Interactions API for new projects (client.interactions.create(model=..., input=...), with the reply at interaction.output_text), which can also keep conversation state on Google's side instead of making you resend it. Google's docs now label the generate_content API used here as legacy, while stating that it remains fully supported. This article sticks with generate_content for the same reason Article 2 stuck with Chat Completions: its stateless, send-the-whole-history shape is the one every provider shares, and it's the shape LiteLLM translates into later in this article.

Your .env file from Article 2 picks up a third line:

.env
# .env
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
GOOGLE_API_KEY=...

System instructions: a third convention

Recall the pattern from Article 2: OpenAI puts the system instruction inside the messages list as a role: "system" entry; Anthropic pulls it out into its own top-level system parameter. Gemini does neither. It goes inside a configuration object:

python
from google.genai import types

response = client.models.generate_content(
    model="gemini-3.8-flash",
    contents="Explain what an API is in two sentences.",
    config=types.GenerateContentConfig(
        system_instruction="You are a concise, helpful assistant.",
        max_output_tokens=4096,
    ),
)

print(response.text)

types.GenerateContentConfig(...) bundles system instructions together with generation parameters like max_output_tokens (previewed here; the next article covers the full set). Notice what isn't in it: temperature. Google strongly recommends keeping it at its default of 1.0 for all Gemini 3 models, warning that lowering it can cause looping or degraded performance. It's the same trend Article 2 flagged, newer reasoning models locking that knob down, and Article 4 comes back to it. The pattern to notice: three providers, three different places to put the exact same concept. OpenAI: a message. Anthropic: a top-level argument. Gemini: a field inside a config object. None of these is wrong, they're just independent design decisions made by three different teams, and memorizing all three is precisely the kind of friction that motivates the rest of this article.

One more dimension from Article 2's comparison worth closing out while it's on screen: max_output_tokens here is optional, same as OpenAI's output cap, unlike Anthropic's max_tokens, which Article 2 called out as genuinely required. Leave it out and Gemini generates until it decides it's done or hits the model's own hard limit.

Streaming with Gemini

python
stream = client.models.generate_content_stream(
    model="gemini-3.8-flash",
    contents="Write a short poem about the ocean.",
)

for chunk in stream:
    print(chunk.text, end="", flush=True)

A fourth convention, though a pleasant one this time: generate_content_stream (a distinct method, rather than a stream=True flag on the same call) returns an iterator of the same response objects you already know, so each chunk has that same convenient .text property. No .delta unwrapping needed here, unlike OpenAI's streaming shape from Article 2.

Multi-turn conversations with Gemini

The single-string shortcut for contents only works for one-off questions. A real conversation needs the same thing Article 2 built for OpenAI and Anthropic: a growing history, resent on every call. Gemini's version of that history has two real differences worth knowing before you write it from memory out of habit:

python
from google.genai import types

contents = []

while True:
    user_input = input("You: ")
    if user_input.lower() in ("quit", "exit"):
        break

    contents.append({"role": "user", "parts": [{"text": user_input}]})

    response = client.models.generate_content(
        model="gemini-3.8-flash",
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction="You are a helpful assistant.",
        ),
    )
    reply = response.text
    print("Assistant:", reply)

    contents.append({"role": "model", "parts": [{"text": reply}]})

Same loop shape, two dict-format differences

  • The role is "model", not "assistant". OpenAI and Anthropic both call the model's own turns assistant; Gemini calls them model. Paste an "assistant" role into a Gemini contents list out of habit and it'll be rejected.
  • Each turn's text sits inside a "parts" list, not a plain "content" string. {"role": "user", "parts": [{"text": user_input}]} instead of {"role": "user", "content": user_input}. This is because a single Gemini turn can genuinely contain multiple parts (text plus an image, for instance), so even a plain text turn keeps that list structure. For everything in this article, a single-item parts list with one {"text": ...} dict is all you need.

As with Claude in Article 2, only the reply's text goes back into the history. Gemini 3 models can attach a "thought signature" to a reply, an encrypted marker of their reasoning, and Google's docs say that for plain text conversations it isn't strictly validated, while recommending you send it back when one is returned, for best reasoning quality. A plain-text history works for this article. If you'd rather not manage that detail by hand, the SDK's built-in chat helper, client.chats.create(model=...), keeps each reply's full content, signature included, in the history for you.

Other providers, briefly

OpenAI, Anthropic, and Google cover most real-world usage, but the wider ecosystem is large. A couple worth knowing exist, without a full code walkthrough for either:

  • Cohere focuses heavily on embeddings and multilingual support, and shows up often in retrieval-heavy applications for that reason specifically.
  • Plenty of others (Mistral, xAI's Grok, and various API front-ends for open-source models) round out the space, each with its own SDK and its own small conventions.

You don't need to memorize any of these. The point of this section is narrower: once you've felt the friction of two providers, then three, the pattern is obvious enough that the actual number of providers stops mattering. Which brings us to the fix.

LiteLLM: one interface, many providers

terminal
pip install "litellm>=1.83.0"

Security note

A security note before anything else, because it's a real lesson rather than a footnote: on March 24, 2026, two LiteLLM releases published to PyPI, 1.82.7 and 1.82.8, were compromised with credential-stealing code that harvested environment variables, which is exactly where your API keys live. It was a supply-chain attack on the package, not a flaw in how LiteLLM works, and LiteLLM's maintainers have confirmed 1.82.6 and earlier, and 1.83.0 onward, as clean. That's what the >=1.83.0 in the install line is for: it guarantees you can't land on either bad release. And if you ever did install one of those two versions, rotate every API key that was in that environment.

LiteLLM is a library that wraps all of the above (and dozens more) behind a single, consistent, OpenAI-shaped interface. Every call looks like an OpenAI Chat Completions call, regardless of which provider is actually answering:

python
import os
from dotenv import load_dotenv
import litellm

load_dotenv()

response = litellm.completion(
    model="gpt-5.5",
    messages=[{"role": "user", "content": "Explain what an API is in two sentences."}],
)
print(response.choices[0].message.content)

response = litellm.completion(
    model="claude-sonnet-5",
    messages=[{"role": "user", "content": "Explain what an API is in two sentences."}],
)
print(response.choices[0].message.content)

response = litellm.completion(
    model="gemini/gemini-3.8-flash",
    messages=[{"role": "user", "content": "Explain what an API is in two sentences."}],
)
print(response.choices[0].message.content)

Read that carefully: all three calls use the exact same shape, litellm.completion(model=..., messages=...), the exact same OpenAI-style messages list, and the exact same response path, response.choices[0].message.content, regardless of which provider is behind it. LiteLLM standardizes every provider's response back into OpenAI's shape, so the differences from earlier in this article (system-as-message vs. top-level vs. config field, .choices[0].message.content vs. filtering Claude's text blocks vs. .text) all disappear from your code.

Fig. 1 — LiteLLM sits between your code and every provider, translating one consistent call shape into each provider's own convention.

Three things make that work

  • Authentication is still per-provider. LiteLLM doesn't remove the need for an OpenAI key, an Anthropic key, and a Google key; it just reads whichever one it needs from your environment automatically (OPENAI_API_KEY, ANTHROPIC_API_KEY, GOOGLE_API_KEY), based on the model string. This is exactly why load_dotenv() still runs before any of these calls.
  • The model string tells LiteLLM which provider to route to. OpenAI and Anthropic model names are recognized directly, gpt-5.5 and claude-sonnet-5 need no prefix. Most other providers need a provider/model-name prefix, which is why the Gemini call above uses gemini/gemini-3.8-flash instead of the bare name.
  • Provider quirks get absorbed, not just renamed. Both of Claude's surprises from Article 2 disappear here. LiteLLM fills in Anthropic's required max_tokens for you (it defaults to the model's maximum output, so pass your own max_tokens= if you want a tighter cost ceiling), and it pulls Claude's thinking out of message.content, so that field holds only the answer, with the reasoning available separately as message.reasoning_content.

Streaming works the same way, with the same stream=True flag from Article 2's OpenAI example, now working identically no matter which provider string you pass:

python
stream = litellm.completion(
    model="claude-sonnet-5",
    messages=[{"role": "user", "content": "Write a short poem about the ocean."}],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)

A simple model router

One genuinely practical thing LiteLLM's uniformity buys you: routing different queries to different models based on how demanding they are, without rewriting any call-handling logic, since every provider now speaks the same shape:

python
def choose_model(prompt: str) -> str:
    """A deliberately simple router: short prompts go to a cheap, fast
    model; anything longer is assumed to need more reasoning capability."""
    if len(prompt) < 100:
        return "gemini/gemini-3.5-flash-lite"
    return "claude-sonnet-5"


def ask(prompt: str) -> str:
    model = choose_model(prompt)
    response = litellm.completion(
        model=model,
        messages=[{"role": "user", "content": prompt}],
    )
    print(f"[routed to {model}]")
    return response.choices[0].message.content


print(ask("What's 12 * 7?"))
print(ask("Walk me through the trade-offs between a monolith and microservices for a 5-person startup building a B2B SaaS product."))
Fig. 2 — The router only ever decides a model-name string; the call underneath is identical either way.

This is deliberately naive, real routing logic would weigh accuracy requirements, latency budgets, and actual cost data rather than just prompt length, but the shape is real: choose_model returns a plain string, and ask doesn't care what that string is. Swap in a smarter choose_model later and nothing else in the function changes. That's the actual payoff of a unified interface: not that it's shorter to type, but that your application logic stops needing to know which provider is underneath it.

What LiteLLM doesn't solve

It's worth being precise about what just got fixed and what didn't. LiteLLM solves exactly one problem: talking to many providers through one consistent call shape. It does not give you chaining, retrieval, persistent memory management, structured output parsing, or tool-calling orchestration, all the other problems Article 1 listed as reasons "just call the API" stops working. LiteLLM is a thin, genuinely useful layer at the model-interface level. It is not, and doesn't try to be, an application framework.

That's precisely the gap LangChain fills, and it's why LangChain's own model interface (which you'll meet in Article 5) solves a similar provider-switching problem to the one LiteLLM solves here, while also giving you everywhere else that raw API calls fall short.
