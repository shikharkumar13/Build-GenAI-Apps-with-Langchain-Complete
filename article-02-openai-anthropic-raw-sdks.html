Article 1 ended on a promise: before LangChain shows up, we spend three articles below the framework line, calling LLM providers directly with nothing but their own SDKs and the raw request/response shape. Everything Article 1 described in the abstract, the next-token loop, the context window, the non-determinism, is about to show up in real API responses you can print and poke at. By the end of this article you'll have built the thing every chat product is quietly built on: a loop that resends a growing list of messages on every single turn.

This article covers the two providers you'll use most: OpenAI and Anthropic. Every code block below is explained line by line underneath it, so even if you've never touched an LLM API before, you should be able to follow exactly what each piece is doing and why it's written that way.

The message format that became an industry standard

Every modern LLM API is built around the same basic idea: instead of sending one block of text and getting one block of text back, you send a list of messages, each tagged with a role, and the model generates the next message in that sequence.

Three roles matter for now:

  • system: instructions that shape how the model should behave for the whole conversation (tone, constraints, persona). Not visible to the end user, set by the developer.
  • user: what the human actually said.
  • assistant: what the model said. You include the model's own past replies here when you want it to have conversational context, more on why that's necessary in a moment.

This role-based format was popularized by OpenAI's Chat Completions API, and it's become close enough to a de facto standard that nearly every provider's API looks structurally similar today. That's a genuinely useful thing to know: the concepts here transfer almost directly to any provider you'll use later. The differences that do exist between providers, and there are a few worth knowing, are exactly what this article walks through.

Fig. 1 — Every call sends the whole conversation as one list of role-tagged messages, not just the newest one.

Setup

You'll need Python 3.10+, and API keys from both providers (OpenAI's platform dashboard and Anthropic's console, both require an account and a payment method attached, since these are metered APIs).

terminal
pip install openai anthropic python-dotenv

Three packages, three jobs: openai is OpenAI's official Python client, anthropic is Anthropic's, and python-dotenv is a small utility that reads key-value pairs out of a .env file and loads them as environment variables your Python process can read.

That last one matters more than it might look. Your API key is a secret: anyone who has it can spend your money. Two rules follow directly from that: never type the key straight into your script, and never commit a file containing it to git. The standard fix is a .env file that stays out of version control (add it to .gitignore), with your code reading the key out of the environment at runtime instead of having it hardcoded:

.env
# .env
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...

Your first OpenAI call

python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

response = client.chat.completions.create(
    model="gpt-5.5",
    messages=[
        {"role": "system", "content": "You are a concise, helpful assistant."},
        {"role": "user", "content": "Explain what an API is in two sentences."},
    ],
)

print(response.choices[0].message.content)

Walking through this line by line

  • import os pulls in Python's built-in module for talking to the operating system, which is what lets us read environment variables in a moment.
  • from dotenv import load_dotenv imports the one function we need from the python-dotenv package.
  • from openai import OpenAI imports the client class from OpenAI's SDK. Note the capitalization: the package is openai (lowercase), the class is OpenAI (a class name, capitalized by Python convention).
  • load_dotenv() actually opens your .env file and copies its contents into the environment for this running process. If you skip this line, os.getenv(...) below will find nothing.
  • client = OpenAI(api_key=os.getenv("OPENAI_API_KEY")) does two things at once: os.getenv("OPENAI_API_KEY") reads the key out of the environment as a plain string, and OpenAI(api_key=...) uses it to build a client object, which is your authenticated connection to OpenAI's servers. You'll reuse this same client for every call in your script instead of re-authenticating each time.
  • client.chat.completions.create(...) is the actual network request. Everything before this line was setup; this is the line that talks to OpenAI over the internet and gets a response back.
  • Inside that call, model picks which model answers you, and messages is the list of role-tagged turns from the section above, here just a system instruction and one user question.
  • The whole thing gets stored in response, an object (not just plain text) with several fields packed into it.

A few things worth noticing in that response object: response.choices is a list; the API can return multiple candidate completions if you ask for them via the n parameter, though almost every real application just uses choices[0]. The actual reply text lives two levels deeper, at response.choices[0].message.content. There's also response.usage, which tells you exactly how many input and output tokens that call consumed, worth logging from day one if you care about cost, which you will.

One more thing worth expecting rather than being surprised by: run this exact script twice, unchanged, and the wording back may differ both times. That's not a bug, it's Article 1's fourth point about LLMs, non-deterministic and occasionally wrong, showing up in the very first call you make. Nothing here is doing anything to suppress that. The classic knob for it is temperature, which gets a full article of its own two articles from now, including a caveat worth knowing early: the newest reasoning models from both providers increasingly lock that knob down or ignore it.

Fig. 2 — response.choices[0].message.content is a path through nested objects, not a shortcut to memorize blindly.

On model choice: gpt-5.5 is the model this series uses for its OpenAI examples. It's a capable general-purpose model and still fully available, but it's no longer OpenAI's newest. As of September 2026 the top of the lineup is the GPT-6 family, with gpt-6-astra as OpenAI's most capable model and gpt-6-sol and gpt-6-luna as cheaper options. That churn is itself the lesson: OpenAI revises its lineup, naming scheme included, often enough that any specific model name in a tutorial goes stale within months. Even the tier names have moved, from "mini" and "nano" in earlier generations to names like Sol and Luna in the newest ones. The pattern that doesn't go stale: there's always a most-capable, most-expensive model, and lighter, cheaper ones for tasks that don't need frontier reasoning. Switching models is a one-string change to model=, so check OpenAI's models page for whatever's current when you're actually building.

One more OpenAI-specific note, so it doesn't surprise you later: OpenAI also has a newer, second API called the Responses API (client.responses.create(...), with the reply available at response.output_text), and recommends it for new projects. Chat Completions remains fully supported, and it's what this article uses on purpose: its list of role-tagged messages is the shape the rest of the industry copied, so it's the version whose concepts carry straight over to every other provider in this series.

Streaming

Without streaming, you wait for the entire response to generate before seeing anything. For anything user-facing, that's a bad experience: streaming lets you print tokens as they're generated, which is what makes ChatGPT (and every other AI chat product) feel responsive instead of frozen.

python
stream = client.chat.completions.create(
    model="gpt-5.5",
    messages=[
        {"role": "user", "content": "Write a short poem about the ocean."},
    ],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
Fig. 3 — Streaming trades one big wait for a steady trickle of small pieces, which is what makes it feel responsive.

What changed, and why each piece is there

  • stream=True is the only difference in the request itself. It tells OpenAI's servers: don't wait until you're done generating, send me pieces as they're ready.
  • Because of that flag, client.chat.completions.create(...) no longer hands back one finished response object. It hands back an iterator, something you loop over, where each item arrives as soon as it's available rather than all at once. That's why we assign it to stream instead of response, and loop over it with for chunk in stream:.
  • Each chunk is a small object carrying one fragment of the eventual full reply, sitting at chunk.choices[0].delta.content. Note delta instead of message: it's a change to append, not a complete message.
  • Not every chunk carries text (the first and last carry metadata instead), so if delta: guards against trying to print None.
  • print(delta, end="", flush=True) prints each fragment without a newline (end="", so the words run together correctly) and forces it to appear immediately (flush=True) instead of waiting in a buffer, which is what actually produces the typewriter effect on screen.

The part that matters most: conversation memory is your job

Recall from Article 1: an LLM has no memory of anything outside its context window. Every API call is completely stateless from the model's point of view. If you want a multi-turn conversation, you are responsible for resending the entire conversation history on every single call:

python
messages = [{"role": "system", "content": "You are a helpful assistant."}]

while True:
    user_input = input("You: ")
    if user_input.lower() in ("quit", "exit"):
        break

    messages.append({"role": "user", "content": user_input})

    response = client.chat.completions.create(
        model="gpt-5.5",
        messages=messages,
    )
    reply = response.choices[0].message.content
    print("Assistant:", reply)

    messages.append({"role": "assistant", "content": reply})

Step by step

  • messages = [{"role": "system", ...}] starts the conversation history as a list containing just the system instruction. This list is going to grow for as long as the conversation runs.
  • while True: starts a loop with no built-in end condition, meaning it runs forever until something inside it explicitly stops it. That's intentional here: we don't know in advance how many turns the conversation will have.
  • input("You: ") pauses the script and waits for the person at the keyboard to type something and press enter.
  • The if user_input.lower() in ("quit", "exit"): break line is that explicit stop condition: type "quit" or "exit" (in any capitalization, thanks to .lower()) and break exits the while loop.
  • messages.append({"role": "user", "content": user_input}) adds what the person just typed onto the end of the growing history, tagged as a user turn.
  • The client.chat.completions.create(...) call looks just like before, except messages is now that whole growing list, not a fresh one-off list. This is the part to actually notice: every single call sends the full conversation so far, not just the newest message.
  • reply = response.choices[0].message.content pulls the text back out, same as the very first example.
  • messages.append({"role": "assistant", "content": reply}) adds the model's own reply back onto the history, so the next call includes it. Skip this line and the model would have no idea what it just said a moment ago.
Fig. 4 — Each call resends the entire growing history. Nothing is remembered by the model itself; you're rebuilding the whole context every time.

This is a genuinely important thing to internalize, because it has two direct consequences: cost grows with conversation length, since you're re-paying for the whole history on every turn, and eventually you'll hit the model's context window limit and need a strategy for trimming or summarizing old messages. We'll build that strategy properly in Article 8, the memory article. For now, just notice that "remembering" is something you engineer, not something the model does for you.

Moving to Anthropic's Claude API

The concepts transfer directly. The syntax has a few real differences worth knowing precisely, because they're the kind of thing that produces a confusing error message if you assume OpenAI's shape works everywhere.

python
import os
from dotenv import load_dotenv
from anthropic import Anthropic

load_dotenv()
client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=4096,
    system="You are a concise, helpful assistant.",
    messages=[
        {"role": "user", "content": "Explain what an API is in two sentences."},
    ],
)

reply = "".join(block.text for block in response.content if block.type == "text")
print(reply)

Same shape, four real differences

  • system is its own top-level parameter, not a message inside the messages list. Anthropic's messages array only ever contains user and assistant turns. If you paste in a {"role": "system", ...} dict here out of habit, the API will reject it.
  • max_tokens is required, not optional. OpenAI will happily run without you specifying an output cap; Anthropic's API will reject the request if you leave it out. 4096 here is a safety cap on total output, not a target length, and on current Claude models "total output" covers more than the visible answer, which the last point below explains.
  • client.messages.create(...) is the method name, where OpenAI used client.chat.completions.create(...). Easy to typo if you're switching between the two.
  • The response is a list of content blocks, and the first one isn't guaranteed to be text. claude-sonnet-5 has adaptive thinking switched on by default: for anything it judges non-trivial, it reasons internally before answering, and that reasoning comes back as a thinking block sitting ahead of the answer's text block. That's why this code doesn't reach for response.content[0].text, a line you'll still find in plenty of older tutorials, which now fails with an AttributeError whenever block zero is a thinking block. Instead, "".join(block.text for block in response.content if block.type == "text") walks every block, keeps only the text ones, and joins them into one string. Those thinking tokens also count against max_tokens, which is why the cap here is a roomy 4096. The same list-of-blocks structure is how Claude hands back tool-use requests too, which Article 12 covers properly.

Anthropic's lineup, as of September 2026, runs from Claude Fable 5.1 at the top (claude-fable-5-1, for the most demanding reasoning and long-horizon agentic work), through an Opus tier (claude-opus-5-5, which Anthropic suggests as the default starting point when you're unsure), a Sonnet tier (claude-sonnet-5, used throughout this series for its balance of speed and capability), and a Haiku tier (claude-haiku-4-5-20251001, fastest and cheapest). Same advice as with OpenAI: the specific names will keep shifting, the tiered capability-versus-cost structure won't.

Streaming with Claude

python
with client.messages.stream(
    model="claude-sonnet-5",
    max_tokens=4096,
    system="You are a concise, helpful assistant.",
    messages=[
        {"role": "user", "content": "Write a short poem about the ocean."},
    ],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

Same goal, a different SDK shape

  • with client.messages.stream(...) as stream: uses a Python context manager, the with ... as ...: pattern. If that's new to you, the short version is: it opens a connection, hands it to you as stream, and automatically closes it cleanly when the indented block underneath finishes, even if something goes wrong partway through. OpenAI's plain iterator doesn't need this because there's no open connection to clean up in the same way.
  • stream.text_stream is an iterator that yields plain text fragments directly, no .delta.content unwrapping needed. That's a genuinely more convenient shape than OpenAI's version, just a different design choice by Anthropic's SDK authors. It also yields only text: any thinking the model does streams separately and never lands in your printed output, though you may notice a short pause before the first words appear while it thinks.
  • The print(text, end="", flush=True) line does exactly the same job as it did in the OpenAI example: print without a newline, and don't buffer.

The conversation loop, Claude version

python
system_prompt = "You are a helpful assistant."
messages = []

while True:
    user_input = input("You: ")
    if user_input.lower() in ("quit", "exit"):
        break

    messages.append({"role": "user", "content": user_input})

    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=4096,
        system=system_prompt,
        messages=messages,
    )
    reply = "".join(block.text for block in response.content if block.type == "text")
    print("Assistant:", reply)

    messages.append({"role": "assistant", "content": reply})

Structurally identical to the OpenAI version: same while True loop, same input() and break exit condition, same pattern of appending the user's message before the call and the assistant's reply after. The only real differences are the two you already know from the first Claude example: system_prompt is tracked as its own separate variable instead of living inside messages, and the reply is assembled from the response's text blocks instead of read from response.choices[0].message.content. Notice, too, that only the reply's text goes back into messages, not any thinking block. That's fine: Anthropic's documentation states that earlier assistant turns don't need to carry their thinking blocks, so a plain-text history works exactly as it did with OpenAI.

A brief note on thinking

You've already met this above without asking for it. Claude's current models think adaptively: before answering, they decide for themselves whether a request deserves internal step-by-step reasoning, and how much, which noticeably improves quality on multi-step problems. On claude-sonnet-5 it's on by default. If you come across older tutorials passing thinking={"type": "enabled", "budget_tokens": ...} to set an explicit reasoning budget, that manual form has been removed on current models and now returns a 400 error; how deeply Claude thinks is steered with an effort setting instead, and thinking can be switched off entirely with thinking={"type": "disabled"}. We'll leave it on its default here. Controlling it properly belongs with the rest of the generation-tuning knobs in Article 4.

None of these differences are large individually. Collectively, they're exactly the kind of repetitive, provider-specific glue code that gets tedious the moment you want your application to work with more than one provider, which is precisely the problem the next article runs straight into.

Try it yourself: take a genuinely hard, multi-step reasoning question (a logic puzzle, a tricky refactor, a word problem with a few moving parts) and send the exact same prompt to both the OpenAI script and the Claude script above. Read both answers side by side. You're not looking for a winner so much as a feel for how the two differ in style and approach, since that intuition is worth more than any benchmark score once you're deciding which provider fits a given task.
