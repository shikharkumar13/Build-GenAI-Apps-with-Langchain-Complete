Conversation memory

Article 6 gave Tidewave's assistant a spot in its prompt for history, MessagesPlaceholder. Article 7 gave you chain composition. Neither one actually manages the history itself, you're still the one appending to a Python list and passing it in on every call, exactly like the raw-SDK loop from Article 2. That's fine for a single script running in one process. It stops being fine the moment you have real users: each one needs their own history, kept separate from everyone else's, looked up by something like a session ID rather than a variable sitting in your script's memory.

A brief history of a feature that moved out

If you go looking for how to do this and land on older material, you'll run into an entire family of classes: ConversationBufferMemory, ConversationBufferWindowMemory, ConversationSummaryMemory, and a few more. These were LangChain's original answer to conversation memory, and in LangChain 1.x they're no longer part of the main package at all: import langchain.memory fails outright with ModuleNotFoundError. They survive only in langchain-classic, a separate package LangChain keeps for legacy code, where they're marked deprecated and scheduled for removal in LangChain 2.0; the warning they print points you at create_agent instead. Worth knowing only so that if you find a tutorial built around one of these classes, you recognize it as a signal the material is old, the same way google-generativeai signaled that back in Article 3.

The mechanism that replaced them: RunnableWithMessageHistory

The direct, LCEL-native replacement wraps a chain and manages its history automatically, keyed by a session identifier you provide:

python
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_core.runnables import RunnableLambda
from langchain_core.messages import AIMessage, HumanMessage

def fake_model(messages: list) -> AIMessage:
    return AIMessage(content=f"I can see {len(messages)} messages in this session.")

runnable = RunnableLambda(fake_model)

store = {}

def get_session_history(session_id: str) -> InMemoryChatMessageHistory:
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

with_history = RunnableWithMessageHistory(runnable, get_session_history)

That fake_model function stands in for a real chain here on purpose: it needs no API key, so the whole mechanism is worth actually running rather than taking on faith:

python
config = {"configurable": {"session_id": "user-42"}}

r1 = with_history.invoke([HumanMessage(content="Hi, I'm Sam")], config=config)
r2 = with_history.invoke([HumanMessage(content="What plans do you offer?")], config=config)
r3 = with_history.invoke([HumanMessage(content="And pricing?")], config=config)

print(r1.content)
print(r2.content)
print(r3.content)

Genuine, real output from actually running this:

output
I can see 1 messages in this session.
I can see 3 messages in this session.
I can see 5 messages in this session.
Fig. 1 — The three-step cycle RunnableWithMessageHistory runs on every call: load, run, save back.

That climbing count, 1, then 3, then 5, is RunnableWithMessageHistory doing its actual job: before each call, it loads whatever's already stored for session_id="user-42" and prepends it to the new input; after each call, it appends both the new human message and the model's reply back into that same store. Turn two sees turn one's two messages plus its own new one, three total. Turn three sees all four prior messages plus its own, five total. Nothing about fake_model itself is stateful, all of the memory lives in RunnableWithMessageHistory and the store behind get_session_history.

A second session_id is a completely separate conversation, with its own independent history:

python
r_other = with_history.invoke(
    [HumanMessage(content="Hello")],
    config={"configurable": {"session_id": "user-99"}},
)
print(r_other.content)
output
I can see 1 messages in this session.

user-99 has never talked to this chain before, so it starts fresh at one message, entirely unaffected by everything user-42 said. This is the actual mechanism a multi-user support assistant needs: one chain, one prompt, many independent conversations, separated by nothing more than the string you pass as session_id.

An honest flag before you build on this

Run the code above yourself and you'll see something worth addressing directly, two warnings, not one:

output
LangChainDeprecationWarning: RunnableWithMessageHistory is deprecated. Use LangGraph's built-in persistence instead.
LangChainDeprecationWarning: The class `InMemoryChatMessageHistory` was deprecated in LangChain 1.6.4 and will be removed in 2.0.0

That's real, current, and worth taking seriously rather than ignoring. Since langchain-core 1.6.4, it isn't only the wrapper that's deprecated: the chat-history store classes underneath it, InMemoryChatMessageHistory and the BaseChatMessageHistory interface every other store implements, carry the same notice, with removal slated for LangChain 2.0.

It's the same pattern this series flagged for agents back in Article 1 and Article 7, showing up here too: LangChain is consolidating stateful execution, memory very much included, into LangGraph rather than maintaining a parallel LCEL-native mechanism for it.

RunnableWithMessageHistory still works today, and it's what the overwhelming majority of existing LangChain tutorials, blog posts, and production code you'll read still use. It's also the clearest way to see the concept itself, load a session's history, prepend it, save the new turn, without pulling LangGraph into this series before we're ready to, which is deliberately Article 13, alongside create_agent. Treat it as the thing you're learning to recognize and read, though, not the thing to reach for in a new build: LangChain's own short-term-memory documentation now recommends create_agent with a checkpointer for conversation memory. When this series gets to Article 13, exactly that shows up: the same session-scoped, per-user history idea, with a thread_id playing the role session_id plays here and LangGraph's checkpointer doing the storing.

Wiring memory into Tidewave's assistant

Put together with what Article 6 already built, MessagesPlaceholder, and a real model:

python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from models import get_model

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant for {product}."),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])
model = get_model()
chain = template | model

chat_with_memory = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history",
)

response = chat_with_memory.invoke(
    {"product": "Tidewave", "question": "Hi, I'm having trouble with billing."},
    config={"configurable": {"session_id": "customer-123"}},
)
print(response.text)

get_model() is Article 5's project helper, the same one every article since has called instead of constructing a provider class directly.

Two new arguments, both about telling RunnableWithMessageHistory where things go in a chain that takes a dict instead of a bare message list: input_messages_key="question" says which key in the input dict holds the new message, and history_messages_key="history" says which key the loaded history should be injected under, matching the name given to MessagesPlaceholder("history") in the template exactly. Get that name mismatched between the two and the history silently never reaches the prompt, worth double-checking if memory ever seems to not be "sticking."

Every field from the template, product included, still needs to be in the input dict on every call, RunnableWithMessageHistory only manages the history and question slots, nothing else.

Keeping history from growing forever

Recall from Article 2: every call resends the entire history, so cost and context-window usage both grow with conversation length. trim_messages handles the practical side of that, keeping recent messages while dropping the oldest ones once a budget is exceeded:

python
from langchain_core.messages import trim_messages, SystemMessage, HumanMessage, AIMessage

messages = [
    SystemMessage(content="You are a helpful assistant for Tidewave."),
    HumanMessage(content="Hi, I'm Sam"),
    AIMessage(content="Hello Sam! How can I help?"),
    HumanMessage(content="What plans do you offer?"),
    AIMessage(content="We offer Starter, Team, and Enterprise plans."),
    HumanMessage(content="What's the price of Team?"),
    AIMessage(content="Team is $29/user/month."),
]

trimmed = trim_messages(
    messages,
    max_tokens=6,
    token_counter=len,
    strategy="last",
    include_system=True,
)
Fig. 2 — Real trimmed output: only the oldest single message is dropped, which can strand a reply without the question it answered.

token_counter=len here counts messages, not real tokens, deliberately simplified to keep the example's behavior easy to predict; in production, pass count_tokens_approximately (from langchain_core.messages.utils), a fast local estimate, or a chat model instance, so max_tokens means actual tokens. strategy="last" keeps the most recent messages and drops from the front once over budget; include_system=True keeps the system message pinned regardless of trimming, since losing your assistant's actual instructions to a trim is rarely what you want. Real output from running this: the system message stays, and exactly one message gets dropped, the very first human turn, "Hi, I'm Sam", while its own reply and everything after survives, six messages total once the system message is counted in. Worth noticing that precisely, since it's easy to assume trimming drops in matched pairs (a human turn and its reply together); it doesn't, it drops the single oldest message at a time until the count fits the budget, which can leave a reply sitting without the question that prompted it. That's what start_on is for:

python
trimmed = trim_messages(
    messages,
    max_tokens=6,
    token_counter=len,
    strategy="last",
    include_system=True,
    start_on="human",
)

With start_on="human", trimming keeps going until the history after the system message begins on a human turn, so the orphaned "Hello Sam! How can I help?" goes too, and you're left with the system message plus the last two complete exchanges, five messages. LangChain's own documentation recommends exactly this pairing, strategy="last" with start_on="human", since chat models generally expect a conversation to open on a user turn.

In a real chain, call trim_messages without a message list and it hands you back a Runnable instead of a result, ready to drop into a chain. The natural place is on the history key, between RunnableWithMessageHistory loading the history and the template using it:

python
from operator import itemgetter
from langchain_core.runnables import RunnablePassthrough

trimmer = trim_messages(
    max_tokens=4,
    token_counter=len,
    strategy="last",
    start_on="human",
)

trimmed_chain = (
    RunnablePassthrough.assign(history=itemgetter("history") | trimmer)
    | template
    | model
)

chat_with_trimmed_memory = RunnableWithMessageHistory(
    trimmed_chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history",
)

RunnablePassthrough.assign(...) passes the input dict through unchanged except for the one key it recomputes, here history, replaced by its trimmed version, which is the one RunnablePassthrough trick Article 7 didn't show. One subtlety: this bounds what the model sees on each call, not what's stored. The session's full history keeps growing in the store behind get_session_history; only the window sent to the model stays fixed, which is usually what you want, since the complete transcript is still there if you need it later.
