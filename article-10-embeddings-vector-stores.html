Article 9 ended with Tidewave's documentation loaded and split into chunks, and with an honest limitation: those chunks are just shorter strings. Nothing about them yet says what they're about, so there's no way to ask "which chunk answers this question?" This article is where they become searchable by meaning, in two steps: embeddings turn each chunk into numbers, and a vector store finds the nearest ones fast.

What an embedding actually is

An embedding model turns text into a vector, a list of numbers, positioned in space such that text with similar meaning ends up at nearby points and text with different meaning ends up far apart. That's the entire idea. "Refund policy" and "how do I get my money back" land close together despite sharing almost no words, because an embedding model captures meaning, not vocabulary. This is what makes "search by meaning" possible at all, and it's the piece that turns Article 9's chunks into something a retriever can actually work with.

Fig. 1 — Two billing-related sentences land near each other; an unrelated sentence lands far away, regardless of exact wording.

LangChain's Embeddings interface

Same pattern as BaseChatModel from Article 5: one shared interface, embed_documents for a batch of texts and embed_query for a single one, implemented independently by each provider's integration package.

python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector = embeddings.embed_query("What plans does Tidewave offer?")

text-embedding-3-small here is one of OpenAI's two current embedding models, which its documentation still calls its newest and most performant, 1536 dimensions by default (its bigger sibling, text-embedding-3-large, produces 3072). Worth a specific warning: if you construct OpenAIEmbeddings() with no model argument at all, the class falls back to text-embedding-ada-002, an older model OpenAI has since surpassed on quality and price. That's a different kind of construction-time trap than ChatOpenAI's silently-ignored temperature from Article 5, there the value you pass gets dropped; here the value you don't pass gets a stale one, but the lesson is the same either way: a plausible-looking default constructor call doesn't always do what you'd assume, so always pass model explicitly.

Gemini follows the identical shape:

python
from langchain_google_genai import GoogleGenerativeAIEmbeddings

embeddings = GoogleGenerativeAIEmbeddings(model="gemini-embedding-001")

Google now has a newer model too, gemini-embedding-2, which is multimodal (it can embed images and other media, not just text) and takes task instructions inside the input text rather than through a task_type parameter. This series uses the text-only gemini-embedding-001, still fully available, because LangChain's GoogleGenerativeAIEmbeddings sets task_type for you automatically, RETRIEVAL_DOCUMENT when embedding chunks and RETRIEVAL_QUERY when embedding a question, which is exactly the style gemini-embedding-001 expects.

One asymmetry worth knowing before you design anything around it: Anthropic doesn't offer an embeddings model at all. Its documentation says so directly, there's no AnthropicEmbeddings class, no embeddings endpoint on its API, nothing to import. What Anthropic's docs do is point you at a third party, Voyage AI (currently its voyage-4 family), which has its own LangChain package, langchain-voyageai. Tidewave's get_model() helper from Article 5 defaults to Claude for chat, and that default keeps working fine everywhere in this series that calls get_model(). But the embeddings step specifically has to come from a different provider, OpenAI, Gemini, or Voyage; there's no Claude option on this particular piece, and no amount of provider-agnostic code design changes that fact.

Building intuition with real numbers

Actually calling an embeddings API needs a key and a network request, same limitation as every model call in this series. But the core idea, similar meaning produces closer vectors, is worth seeing with real, computed numbers rather than taken on faith. Here's a deliberately tiny stand-in, clearly not a real embedding model, just counting shared vocabulary words to illustrate the geometry:

python
import re, math
from collections import Counter

VOCAB = ["plan", "bill", "refund", "team", "enterprise", "project", "slack"]

def toy_vectorize(text: str) -> list[float]:
    # crude plural stripping so "plans"/"refunds" still hit the singular
    # vocab entries; a real embedding model needs nothing like this
    words = [w.rstrip("s") if w.endswith("s") and len(w) > 3 else w
             for w in re.findall(r"[a-z]+", text.lower())]
    counts = Counter(words)
    return [float(counts.get(term, 0)) for term in VOCAB]

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a, norm_b = math.sqrt(sum(x * x for x in a)), math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0

v1 = toy_vectorize("Tidewave offers three plans: Starter, Team, and Enterprise.")
v2 = toy_vectorize("The Team plan is billed per seat with custom Enterprise pricing.")
v3 = toy_vectorize("Connect Slack to get project notifications posted to a channel.")

print(cosine_similarity(v1, v2))
print(cosine_similarity(v1, v3))

Genuine, computed output:

output
1.0000000000000002
0.0

That first number is 1 plus a floating-point rounding error (three divided by the square root of three, squared), so read it as exactly 1.0. Both plan-and-pricing sentences hit exactly the same three vocabulary buckets, plan, team, enterprise, so this tiny model scores them as identical in direction, a perfect 1.0, even though the wording is quite different. The Slack sentence shares none of those buckets and scores a flat 0.0. That perfect 1.0 is itself worth noticing: it's a symptom of how coarse a seven-word bag-of-words vocabulary really is, two sentences don't have to mean the same thing to hit the same buckets, they just both need to mention a plan, a team, and Enterprise. A real embedding model works in thousands of dimensions learned from actual language patterns rather than a hand-picked word list, which is exactly why it doesn't saturate at a perfect score nearly as easily, and why it catches similarity between sentences that share no vocabulary at all. The geometric idea carries over regardless: similarity as a number between -1 and 1, closer meaning as a higher score.

Vector stores: why you need one

A handful of vectors, you could compare by hand. Tidewave's actual documentation, dozens or hundreds of chunks, real production content, thousands, needs something built to do that comparison fast at scale. That's what a vector store is: storage for vectors, plus an index that finds the closest ones to a query vector without checking every single one individually.

Chroma is a solid default for this series: it runs in-process, no separate server or account needed, which makes it genuinely easy to actually run the examples below yourself.

python
from langchain_chroma import Chroma

vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name="tidewave_docs",
)

results = vectorstore.similarity_search("How do refunds work?", k=2)

chunks here is exactly what Article 9 produced, running RecursiveCharacterTextSplitter over Tidewave's docs. Chroma.from_documents embeds every chunk and stores the resulting vectors; similarity_search embeds the query the same way and returns the k closest chunks.

Give the collection a name, as collection_name does here, even for throwaway experiments. Leave it out and Chroma uses a collection called "langchain", and within one Python process every unnamed from_documents call adds to that same collection rather than starting fresh. Run the cell twice in a notebook and every chunk is stored twice, so duplicates start showing up in your results; switch to a different embedding model in the same session and the next call fails outright with Collection expecting embedding with dimension of 1536, got 7, because the collection still holds the first model's vectors.

A real gotcha, found by actually running this

Building this article's examples surfaced something concrete enough to walk through directly, because it's the kind of thing that silently produces wrong results if you don't know to check for it. To run the toy vectorizer through Chroma, it needs wrapping in LangChain's Embeddings interface, which takes just two methods:

python
from langchain_core.embeddings import Embeddings

class ToyEmbeddings(Embeddings):
    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        return [toy_vectorize(t) for t in texts]

    def embed_query(self, text: str) -> list[float]:
        return toy_vectorize(text)

vectorstore = Chroma.from_documents(
    documents=chunks, embedding=ToyEmbeddings(), collection_name="toy_l2"
)
results = vectorstore.similarity_search("How do refunds work?", k=1)

Querying "How do refunds work?" against Tidewave's real docs this way returned a chunk about GitHub integration as the top result. Not the refunds section. GitHub.

The cause: Chroma's default search uses Euclidean (L2) distance, not cosine similarity, and Euclidean distance is sensitive to vector magnitude in a way cosine similarity isn't. The query vector for "How do refunds work?" is small, a single 1 in the refund slot. The correct "Refunds" chunk mentions refunds four times, so its vector is a 4 in that same slot: exactly the right direction, but at distance 3.0 from the query. The GitHub chunk never mentions refunds at all; it just has a few small counts in other slots, which leaves it at distance 2.65, closer. Push that to the extreme and the problem is plain: a chunk matching none of the vocabulary is an all-zero vector, sitting at distance 1 from the query, nearer than the chunk that's entirely about refunds. That isn't bad luck, it's systematic: under Euclidean distance, anything small, near the origin, can beat a large vector pointing the right way. Direction was right, distance was wrong.

Fig. 2 — Real numbers from this article: unnormalized, raw distance favors the numerically smaller but irrelevant chunk.

The fix is normalizing every vector to length 1 before it goes anywhere near the vector store, one addition to the same toy_vectorize from before:

python
def toy_vectorize(text: str) -> list[float]:
    words = [w.rstrip("s") if w.endswith("s") and len(w) > 3 else w
             for w in re.findall(r"[a-z]+", text.lower())]
    counts = Counter(words)
    vec = [float(counts.get(term, 0)) for term in VOCAB]
    norm = math.sqrt(sum(x * x for x in vec))
    return [x / norm for x in vec] if norm else vec

With that one change, rebuilding the store (under a fresh collection_name, say "toy_normalized", for the reason given above) and running the exact same query against the exact same documents correctly returns the "Refunds" section first. Once every vector has length 1, Euclidean distance and cosine similarity always rank results in the same order, so magnitude can no longer mislead the search. The other fix is to tell Chroma to use cosine distance in the first place, one argument at construction:

python
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=ToyEmbeddings(),
    collection_name="toy_cosine",
    collection_configuration={"hnsw": {"space": "cosine"}},
)

This is exactly why it's worth knowing, even though real embedding providers mostly handle it for you. OpenAI's documentation states that its embeddings are normalized to length 1, and that cosine similarity and Euclidean distance therefore give identical rankings. Gemini's gemini-embedding-001 is normalized at its default 3,072 dimensions, but if you ask for fewer with output_dimensionality (768 or 1,536, say, to save storage), Google's documentation says you must normalize those vectors yourself. So you won't hit this with OpenAIEmbeddings or a default GoogleGenerativeAIEmbeddings in normal use. But if you shrink Gemini's dimensions, write a custom Embeddings class, cache vectors from somewhere else, or debug a vector store returning results that feel wrong despite everything looking correct, normalization, or the store's distance setting, is the first thing worth checking.

Persistence, and other stores worth knowing exist

Everything above lives in memory and disappears when the process exits. Add persist_directory to write the collection to disk and reload it later without re-embedding everything from scratch:

python
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name="tidewave_docs",
    persist_directory="./tidewave_chroma_db",
)

Chroma isn't the only option, worth knowing exist without a full detour here. langchain-core itself ships an InMemoryVectorStore, no extra package at all, handy for tests and tiny prototypes. FAISS is another common in-process choice, oriented more toward raw search speed than Chroma's broader feature set; it now has its own standalone package, langchain-faiss, so you don't need the sunset langchain-community from Article 9 to use it. Pinecone and similar hosted services, via langchain-pinecone and friends, trade the "no server needed" convenience for a managed, scalable backend once a project outgrows a single machine. The Embeddings and VectorStore interfaces are consistent enough across LangChain's integrations that switching between them later is a constructor change, not a rewrite, the same story as swapping chat model providers back in Article 5.
