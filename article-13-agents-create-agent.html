Look back at what Article 12 actually built: call the model, check tool_calls, run the tool, append a ToolMessage, call the model again. That loop, written by hand, is what "agent" means. This article doesn't introduce a new idea, it introduces the tool that runs that exact loop for you: create_agent. It's also where LangGraph finally enters this series, six articles after Article 7 first mentioned it was coming, because this is the first thing in the whole series that genuinely needs it. There's nothing extra to install for it, either: langgraph is a dependency of the langchain package itself, so it has been sitting in your environment since Article 5.

What create_agent actually is

create_agent, from langchain.agents import create_agent, is LangChain's current high-level API for building agents, and it's built directly on LangGraph's runtime underneath. It replaces AgentExecutor, LangChain's older agent-building class, and the replacement is more complete than a deprecation warning: AgentExecutor isn't importable from langchain.agents at all anymore, confirmed by trying it directly against the current package. It still exists, just not there, it moved to a separate langchain_classic package, the same migration this series already saw happen to the old memory classes back in Article 8. What it returns isn't a chain in the LCEL sense from Article 7, it's a compiled LangGraph graph, but that graph is still a Runnable, so .invoke() and .stream() work exactly the way they always have since Article 5.

python
from langchain.agents import create_agent
from models import get_model

model = get_model()
agent = create_agent(
    model,
    tools=[check_subscription_status],
    system_prompt="You are a helpful assistant for Tidewave.",
)

model and tools are the same objects from Articles 5 and 12, get_model() and the @tool-decorated check_subscription_status, unchanged. (create_agent will also take a model string directly, create_agent("anthropic:claude-sonnet-5", ...), the same init_chat_model format get_model() wraps; this series keeps passing get_model() so the model choice stays in one place.) create_agent is the piece that turns "a model that can request a tool" into "something that actually runs the tool and keeps going until it has a real answer."

Fig. 1 — Same sequence of events either way. create_agent doesn't do anything new; it just runs Article 12's loop so you don't maintain it by hand.

Calling it, and what comes back

Agents take and return a slightly different shape than the chains from earlier articles, a dict with a messages key, rather than a bare message list or a single string:

python
result = agent.invoke({
    "messages": [{"role": "user", "content": "What's my subscription status? My email is sam@example.com"}]
})

result["messages"] holds the full conversation, including every intermediate step the agent took to get there, the tool request, the tool's result, and the final reply, not just the last message. The answer itself is the last one, and it's worth reading with .text rather than .content, for the same reason as Article 5: with a real Claude model, the intermediate AIMessage that requested the tool carries thinking and text blocks alongside the request, so .content is a list, not a string.

python
print(result["messages"][-1].text)

tools is a list for a reason, too. Give the agent several and the model picks among them on each pass, which is the decision Article 12 ended on: it may request one tool, several at once (the agent runs every requested call before going back to the model), or none, answering directly when the question doesn't need any customer's data. The loop keeps going until the model replies without a tool request.

Watching the loop actually run

Deciding to call the tool needs a live model, same as Article 12. But this article's stand-in is worth a beat of explanation before seeing it, since it's more involved than the simple RunnableLambda swaps from Articles 8, 11, and 12: create_agent calls .bind_tools() on whatever model it's given internally, so a stand-in has to actually implement that method, along with LangChain's real message-generation interface, not just return a message from a lambda. Here's the smallest version that does:

python
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.outputs import ChatResult, ChatGeneration
from langchain_core.messages import AIMessage, ToolMessage

class FakeAgentModel(BaseChatModel):
    """Stand-in so the full agent loop can run with no API key. First
    call: request the tool. Second call, once it sees a ToolMessage
    in the history: give a final answer using that result."""

    def _generate(self, messages, stop=None, run_manager=None, **kwargs) -> ChatResult:
        tool_result = next((m.content for m in messages if isinstance(m, ToolMessage)), None)
        if tool_result:
            message = AIMessage(content=f"Here's your status: {tool_result}")
        else:
            message = AIMessage(
                content="",
                tool_calls=[{
                    "name": "check_subscription_status",
                    "args": {"customer_email": "sam@example.com"},
                    "id": "call_1",
                    "type": "tool_call",
                }],
            )
        return ChatResult(generations=[ChatGeneration(message=message)])

    def bind_tools(self, tools, **kwargs):
        return self

    @property
    def _llm_type(self) -> str:
        return "fake-agent-model"


agent = create_agent(
    FakeAgentModel(),
    tools=[check_subscription_status],
    system_prompt="You are a helpful assistant for Tidewave.",
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "What's my subscription status? My email is sam@example.com"}]
})
for m in result["messages"]:
    print(type(m).__name__, "->", m.content)

What each piece is doing

  • _generate is the one method every chat model must implement. LangChain calls it with the full message history so far and expects a ChatResult wrapping a ChatGeneration wrapping the actual AIMessage back, that nested shape is real LangChain plumbing, not something this stand-in invented.
  • The branching logic is the whole "brain" of this fake model. next((m.content for m in messages if isinstance(m, ToolMessage)), None) checks whether a tool result is already sitting in the history. The first time through, there isn't one, so it returns the tool-call request. The second time, the agent has already appended a ToolMessage with the real result, so this branch fires instead and produces a normal final answer using it.
  • bind_tools just returns self, ignoring the tools it's handed. A real provider integration would use this method to actually tell the provider's API which tools are available; this stand-in already knows what it's going to do regardless, so there's nothing to configure. It exists purely to stop create_agent's internal call to .bind_tools() from failing.

Genuine output, and this is the entire point of the article:

output
HumanMessage -> What's my subscription status? My email is sam@example.com
AIMessage ->
ToolMessage -> Team plan, active, next billing date 2026-09-15
AIMessage -> Here's your status: Team plan, active, next billing date 2026-09-15
Fig. 2 — The real, verified message sequence from this article's run: request, tool result, then a final answer that actually uses it.

With a real Claude model, that second line wouldn't be empty: its content would hold the thinking and "let me check" text blocks from Article 12, and printing m.text instead of m.content gives just the text. The shape of the run is identical either way.

Nobody wrote a loop. check_subscription_status.invoke(...) ran, the result got appended as a ToolMessage, and the model got called a second time, all of it happening inside agent.invoke(), the exact sequence Article 12 built by hand, now automated. One more real detail worth knowing: the system_prompt gets prepended as an actual SystemMessage on every internal call the agent makes, confirmed by inspecting what FakeAgentModel._generate actually receives, but it doesn't appear in result["messages"], which only tracks the conversational turns.

Closing the loop from Article 8

Recall the honest flag from Article 8: RunnableWithMessageHistory carries a deprecation warning pointing at LangGraph's own persistence. This is that. Agents remember across turns with a checkpointer and a thread_id, not RunnableWithMessageHistory at all:

python
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    FakeAgentModel(),  # get_model() in production
    tools=[check_subscription_status],
    system_prompt="You are a helpful assistant for Tidewave.",
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "customer-123"}}
agent.invoke(
    {"messages": [{"role": "user", "content": "What's my subscription status? My email is sam@example.com"}]},
    config=config,
)
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Thanks! Which plan was that again?"}]},
    config=config,
)
for m in result["messages"]:
    print(type(m).__name__, "->", m.content)

Genuine output from the second call:

output
HumanMessage -> What's my subscription status? My email is sam@example.com
AIMessage ->
ToolMessage -> Team plan, active, next billing date 2026-09-15
AIMessage -> Here's your status: Team plan, active, next billing date 2026-09-15
HumanMessage -> Thanks! Which plan was that again?
AIMessage -> Here's your status: Team plan, active, next billing date 2026-09-15

The second call only sent one new message, yet the result holds six. The checkpointer loaded the first turn's four messages for customer-123 before the model ran, so FakeAgentModel found the earlier ToolMessage already in the history and answered without calling the tool again. The canned reply is the stand-in's limit; the history it was given is the real mechanism. Invoke with a different thread_id and the agent starts from an empty history.

thread_id plays exactly the role session_id played back in Article 8, one growing history per id, looked up automatically on every call. InMemorySaver is the simplest checkpointer, in-memory only, gone when the process exits, the same trade-off Article 10's Chroma setup had before persist_directory entered the picture. For anything that has to survive a restart, LangGraph ships database-backed checkpointers as separate packages, SqliteSaver from langgraph-checkpoint-sqlite and PostgresSaver from langgraph-checkpoint-postgres, and swapping one in is a constructor change. This is the mechanism Article 8 pointed toward without using yet. Article 8's other problem, a history that grows forever, still applies per thread; the create_agent answer to it is middleware, covered next.

Putting a ceiling on the loop

Cost note

"Keeps going until the model replies without a tool request" has an uncomfortable corollary: a model that keeps requesting tools keeps the loop running. LangGraph does have a safety stop, the recursion_limit, but its default is now roughly 10,000 steps (older LangGraph versions used 25, which is the number most tutorials still quote), so in practice it won't save you from a model stuck calling the same tool over and over, each call billed. Set a real ceiling yourself:

python
from langchain.agents.middleware import ModelCallLimitMiddleware

agent = create_agent(
    model,
    tools=[check_subscription_status],
    system_prompt="You are a helpful assistant for Tidewave.",
    middleware=[ModelCallLimitMiddleware(run_limit=5)],
)

run_limit=5 allows at most five model calls per invoke(). Tested with a stand-in that requests a tool on every call, the agent stopped after the fifth and ended with a final AIMessage reading Model call limits exceeded: run limit (5/5) instead of looping on. Pass exit_behavior="error" if you'd rather it raise. The blunter alternative is lowering recursion_limit per call, agent.invoke(..., config={"recursion_limit": 10}), which raises GraphRecursionError when hit.

Middleware, and where create_agent stops being the right layer

That middleware= argument is create_agent's main customization point, and LangChain ships a set of ready-made pieces for it. A few worth knowing by name: SummarizationMiddleware condenses older messages once a thread's history gets long, the agent-era answer to Article 8's trim_messages; HumanInTheLoopMiddleware pauses the run before chosen tools execute so a person can approve, edit, or reject the call (it needs a checkpointer, since the paused run has to be resumed later); ToolRetryMiddleware and ModelRetryMiddleware retry failed calls. Separately, a response_format= argument makes the agent's final answer a validated Pydantic object, the same idea as Article 6's with_structured_output, applied to the end of a whole agent run.

Everything in this article covers the common shape well: a model, a handful of tools, a loop that runs until there's a real answer. create_agent plus middleware is an opinionated layer over LangGraph for that shape. Custom branching logic, multiple cooperating agents, or control flow that middleware can't express is LangGraph's graph-building API territory instead, nodes and edges you wire up yourself, a larger topic than this series has room for. Worth knowing it's there as the next layer down; not worth reaching for until create_agent specifically can't do what you need.
