Look back at how Article 6 ended: format a prompt with template.invoke({...}), then separately call .invoke() again on a model with the result. Two steps, two variables, one obvious question: why isn't this just one expression? LCEL, LangChain Expression Language, is the answer, and it's less a separate feature to learn than a consequence of one design decision made consistently across the whole framework.

The one idea underneath everything: Runnable

Every piece of LangChain you've used so far, a prompt template, a chat model, and every piece you're about to use, an output parser, a retriever, later in this series, implements the same shared interface: Runnable. Anything that's a Runnable gets .invoke(), .batch(), and .stream() for free (plus async twins, .ainvoke() and friends), with the same meaning every time: take one input and produce one output, take a list of inputs and produce a list of outputs, or produce an output as a stream of pieces. You've already been using this without the name attached to it: template.invoke({...}) and model.invoke(messages) are the exact same method, defined once, implemented by two different classes.

Python's | operator, normally bitwise OR, is overloaded on Runnable to mean something else entirely: compose. a | b builds a RunnableSequence where a's output becomes b's input. That's the entire mechanism. Nothing about prompts or models is special-cased into it.

python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from models import get_model

template = ChatPromptTemplate.from_messages([
    ("system", "You are a concise, helpful assistant for {product}."),
    ("human", "{question}"),
])
model = get_model()

chain = template | model | StrOutputParser()

response = chain.invoke({"product": "Tidewave", "question": "What plans do you offer?"})
print(response)

get_model() is Article 5's project helper, the same one Article 6 used, reused here again rather than constructing a provider class directly.

Three Runnables, two pipes

  • template | model builds a RunnableSequence where the template's output, a ChatPromptValue, becomes the model's input. You already know this works, Article 6 showed model.invoke() accepting a ChatPromptValue directly; the pipe operator is just automating that same handoff instead of you doing it by hand across two lines.
  • | StrOutputParser() adds a third step: the model's output, an AIMessage, becomes the parser's input, and StrOutputParser does exactly one thing, extract the message's text and return it as a plain string. Note text, not .content: with Claude thinking by default, .content is a list of blocks (Article 5), and StrOutputParser returns only the answer text, the same thing .text gives you, reasoning left out. It's a Runnable too, same as everything else here.
  • chain.invoke({...}) runs the whole sequence in one call: the dict goes into the first step, the template, and from there each step's output flows into the next. chain itself is a Runnable, meaning it can be composed into something larger the exact same way, chains built out of chains, all the way up.
Fig. 1 — RunnableSequence: a straight line, each pipe handing its left side's output to its right side's input.

Rewriting Article 6's classifier as one chain

The structured-output classifier from last article composes exactly the same way, since with_structured_output also returns a Runnable:

python
from typing import Literal
from pydantic import BaseModel, Field

class TicketClassification(BaseModel):
    """Structured classification of a Tidewave support message."""
    category: Literal["billing", "technical", "feature_request", "other"] = Field(
        description="The best-fit category for this support message"
    )
    priority: Literal["low", "medium", "high"] = Field(
        description="How urgently this message needs a response"
    )
    summary: str = Field(description="One-sentence summary of the issue")


classify_template = ChatPromptTemplate.from_messages([
    ("system", "You classify incoming support messages for {product}."),
    ("human", "{message}"),
])
classifier = model.with_structured_output(
    TicketClassification, method="json_schema"
)

classify_chain = classify_template | classifier

result = classify_chain.invoke({
    "product": "Tidewave",
    "message": "My card was charged twice this month and I need a refund ASAP.",
})
print(result.category, result.priority)

That's the entirety of Article 6's "Putting both together" section, minus the intermediate prompt_value variable. Same two pieces, same result, one expression instead of two statements.

RunnableParallel: running steps side by side

Sometimes you want more than one thing done with the same input, not one thing after another. RunnableParallel runs several Runnables against the same input and collects their outputs into a dict, keyed by whatever names you give each branch. This one's worth seeing actually run, with real output, rather than taking on faith, since (unlike the model calls above) it needs no API key at all:

python
from langchain_core.runnables import RunnableParallel, RunnableLambda, RunnablePassthrough

uppercase = RunnableLambda(lambda text: text.upper())
word_count = RunnableLambda(lambda text: len(text.split()))

parallel = RunnableParallel(
    original=RunnablePassthrough(),
    upper=uppercase,
    word_count=word_count,
)

result = parallel.invoke("hello world from tidewave")
print(result)

This actually executes, and here's the genuine output:

output
{'original': 'hello world from tidewave', 'upper': 'HELLO WORLD FROM TIDEWAVE', 'word_count': 4}
Fig. 2 — RunnableParallel: the same input fans out to every branch independently, then fans back in as one combined dict.

Three branches, one input, one dict of results. Two new pieces showed up in that example, worth naming directly:

Two new pieces

  • RunnableLambda wraps an ordinary Python function (even a one-line lambda) so it satisfies the Runnable interface and can sit inside a chain like any other piece. Custom logic, string manipulation, a calculation, a lookup, becomes composable the same way a prompt or a model is.
  • RunnablePassthrough is the identity function as a Runnable: whatever comes in goes out unchanged. On its own that sounds pointless; it earns its place inside something like RunnableParallel, where you want one branch to carry the original input forward untouched while other branches transform it.
Try it yourself: that example needs no API key at all, so it's worth actually running and then adding a fourth branch, a RunnableLambda that reverses the string, or counts vowels, or anything else. Every branch runs against the same original input independently; watch the returned dict grow a key for each one you add.

There's a shorthand worth knowing too: a plain Python dict, piped into or out of a Runnable, gets automatically coerced into a RunnableParallel. {"upper": uppercase, "original": RunnablePassthrough()} | next_step works without writing RunnableParallel(...) explicitly; the dict becomes the first step of the resulting sequence. You'll see this shorthand constantly in LangChain code you read elsewhere; it's exactly the same mechanism, just implicit.

The Tidewave version

Applied to the actual project: enrich the classifier chain so the output carries both the structured classification and the original message, useful the moment downstream code, a future article's tool call, say, needs to reference what the customer actually wrote, not just the extracted category:

python
enriched_chain = RunnableParallel(
    original_input=RunnablePassthrough(),
    classification=classify_template | classifier,
)

result = enriched_chain.invoke({
    "product": "Tidewave",
    "message": "My card was charged twice this month and I need a refund ASAP.",
})
# result["original_input"] -> the original dict
# result["classification"] -> the TicketClassification object

RunnablePassthrough() carries the raw input dict forward unchanged in one branch, while classify_template | classifier, itself a full chain, runs in the other. Both are genuinely Runnable, so nesting one chain inside RunnableParallel as a single branch is nothing special, just composition, the same idea applied one level deeper.

.batch(): the method every chain already has

Because all of this rests on the same Runnable interface, .batch() isn't something you add, it's already there, on any chain:

python
double = RunnableLambda(lambda x: x * 2)
print(double.batch([1, 2, 3]))

Real output: [2, 4, 6]. Swap double for a full template | model chain and .batch() runs multiple inputs for you, instead of writing your own loop around repeated .invoke() calls. It isn't a sequential loop in disguise, either: by default .batch() runs the inputs concurrently on a thread pool, so four slow model calls take roughly as long as one. That's also the thing to watch with a real model: every input is a separate API call hitting your rate limit at once, so for large batches cap it with chain.batch(inputs, config={"max_concurrency": 5}). The same goes for .stream() from Article 5, it's not a special model-only trick, it works on an entire composed chain exactly the same way it worked on a bare model, since a chain is a Runnable too.

Where LCEL stops being the right tool

Everything in this article composes in a straight line: input flows through a fixed sequence of steps to an output. That covers a genuine majority of this series, prompts, models, parsers, and (starting in a few articles) retrieval all chain together this way. It starts to strain the moment your logic needs real control flow. Simple routing is possible, RunnableBranch, or a RunnableLambda that returns a different chain depending on its input, but looping back to an earlier step, carrying state across iterations, or pausing partway through for something like human approval is control flow LCEL was never designed to express cleanly. That's what LangGraph exists for, and it's what LangChain's own create_agent, covered in Article 13, is built on underneath. You won't need it until this series gets there; worth knowing now only so you're not tempted to force a branching agent loop through pipe operators later, when a purpose-built tool is the better fit.
