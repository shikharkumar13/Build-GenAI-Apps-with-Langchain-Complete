Fig. 1. Seven modules, each one article's job, imported by whatever needs it next rather than rewritten. Triage and the agent only meet in main.py.

One design choice runs through all of them: every builder function takes its dependencies as optional arguments, a model, a retriever, an embedding model, and falls back to the real one when you don't pass anything. main.py passes nothing and gets Claude, OpenAI embeddings, and a real vector store. The tests pass stand-ins and get a run that needs no API key at all. It's the same Runnable interchangeability this whole series has leaned on since Article 5, used on purpose.

models.py: Article 5

python
from langchain.chat_models import init_chat_model
from langchain_core.language_models.chat_models import BaseChatModel


def get_model(
    provider_and_model: str = "anthropic:claude-sonnet-5", **kwargs
) -> BaseChatModel:
    """Return a configured chat model for Tidewave's assistant.

    Accepts an init_chat_model-style "provider:model-name" string, so
    swapping the underlying provider anywhere in the project later is a
    one-argument change, not a rewrite. Any extra settings, such as
    reasoning_effort="low", are passed straight through.
    """
    return init_chat_model(provider_and_model, **kwargs)

Exactly Article 5's helper, the version every article since has imported. Every other module gets its model through this one function rather than importing ChatAnthropic directly: swapping providers is a one-argument change here, not a search-and-replace across seven files. It deliberately sets no temperature, since claude-sonnet-5 rejects any non-default sampling parameter with a 400 error (Article 4); anything a particular model does accept, such as reasoning_effort="low" for GPT-5.5, passes straight through **kwargs.

documents.py: Article 9

python
import pathlib
from langchain_core.documents import Document


def load_text_file(path: str) -> Document:
    text = pathlib.Path(path).read_text(encoding="utf-8")
    return Document(page_content=text, metadata={"source": path})


def load_directory(dir_path: str, pattern: str = "*.md") -> list[Document]:
    return [load_text_file(str(p)) for p in sorted(pathlib.Path(dir_path).glob(pattern))]

Unchanged. Recall from Article 9 why this is plain Python rather than langchain-community's DirectoryLoader: that package was sunset, and a Document is two fields, cheap enough to build by hand with no dependency on an archived package.

knowledge_base.py: Articles 9, 10, and 11

python
from langchain_chroma import Chroma
from langchain_core.documents import Document
from langchain_core.embeddings import Embeddings
from langchain_core.retrievers import BaseRetriever
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

from documents import load_directory


def build_retriever(
    docs_path: str = "tidewave_docs",
    embedding: Embeddings | None = None,
    persist_directory: str | None = None,
    k: int = 3,
) -> BaseRetriever:
    embedding = embedding or OpenAIEmbeddings(model="text-embedding-3-small")
    vectorstore = Chroma(
        collection_name="tidewave_docs",
        embedding_function=embedding,
        persist_directory=persist_directory,
        collection_configuration={"hnsw": {"space": "cosine"}},
    )
    if not vectorstore.get(limit=1)["ids"]:  # empty: first run, or in-memory
        docs = load_directory(docs_path)
        chunks = RecursiveCharacterTextSplitter(
            chunk_size=300,
            chunk_overlap=50,
        ).split_documents(docs)
        vectorstore.add_documents(chunks)
    return vectorstore.as_retriever(search_kwargs={"k": k})


def format_docs(docs: list[Document]) -> str:
    return "\n\n".join(d.page_content for d in docs)

Load, split, embed, index, retrieve: Articles 9 through 11 in a few dozen lines, with each of those articles' lessons applied rather than re-learned:

  • A named collection (Article 10), so repeated builds in one process don't pile duplicate chunks into Chroma's shared default collection.
  • Cosine distance (Articles 10 and 11). OpenAI's vectors are normalized, so it ranks the same as Chroma's default Euclidean distance for them, but it also keeps the toy embeddings in the tests ranking correctly.
  • k=3 instead of Article 11's single-result demo, inside the two-to-five starting range Article 11 recommended, so a question that spans two sections of the docs can get both.
  • Persistence (Article 10's persist_directory), with one addition: the store is only filled when it's empty. On first start every chunk gets embedded; on every start after that, the saved index is reused and nothing is re-embedded. Delete the folder after editing the docs to rebuild it.

This module still names OpenAIEmbeddings directly rather than going through get_model(), Article 10's asymmetry: Anthropic has no embeddings model, so this is the one place the project has to name a second provider. The embedding argument is what lets the tests swap in Article 10's toy vectorizer instead.

tools.py: Articles 7, 11, and 12, meeting for the first time

Every earlier article touching retrieval and every earlier article touching tools stayed in its own lane on purpose. Here's where they combine: retrieval itself becomes a tool, so the agent decides when to search the documentation, instead of a fixed pipeline that always does. This is the agentic RAG that Article 11 said this series would reach once tools and agents were in place.

python
from langchain_core.retrievers import BaseRetriever
from langchain_core.tools import BaseTool, tool

from knowledge_base import format_docs


def make_search_docs(retriever: BaseRetriever) -> BaseTool:
    docs_chain = retriever | format_docs

    @tool
    def search_docs(query: str) -> str:
        """Search Tidewave's documentation for information about features, plans, or policies."""
        return docs_chain.invoke(query)

    return search_docs


@tool
def check_subscription_status(customer_email: str) -> str:
    """Check a Tidewave customer's current subscription plan and billing status."""
    fake_db = {
        "sam@example.com": "Team plan, active, next billing date 2026-09-15",
        "priya@example.com": "Starter plan, active",
    }
    return fake_db.get(customer_email.strip().lower(), "No account found for that email.")

retriever | format_docs is Article 7's pipe operator doing what it always does, now building the body of a tool. search_docs wraps that chain in Article 12's @tool decorator, so what used to be a fixed first step in Article 11's RAG chain is something the model can choose to call or skip. It's built inside make_search_docs rather than at import time, so importing tools.py doesn't quietly build a vector store and spend embedding calls; whoever calls the function decides which retriever it searches. check_subscription_status is Article 12's tool with one line changed: it lower-cases and trims the email before the lookup, the normalization step Article 14 used to demonstrate @traceable, since a customer typing Sam@Example.com shouldn't get "No account found".

triage.py: Article 6

Every module so far feeds the agent loop. This one runs alongside it, and it's the one place in the project where ChatPromptTemplate and with_structured_output, Article 6, show up directly rather than through create_agent's internals:

python
from typing import Literal

from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import Runnable
from pydantic import BaseModel, Field

from models import get_model


class TicketClassification(BaseModel):
    """Structured classification of a Tidewave support message."""
    category: Literal["billing", "technical", "feature_request", "other"] = Field(
        description="The best-fit category for this support message"
    )
    priority: Literal["low", "medium", "high"] = Field(
        description="How urgently this message needs a response"
    )
    summary: str = Field(description="One-sentence summary of the issue")


classify_template = ChatPromptTemplate.from_messages([
    ("system", "You classify incoming support messages for Tidewave."),
    ("human", "{message}"),
])


def build_triage(model: BaseChatModel | None = None) -> Runnable:
    classifier = (model or get_model()).with_structured_output(
        TicketClassification, method="json_schema"
    )
    return classify_template | classifier

TicketClassification and the template are Article 6's, unchanged, composed with the same pipe operator as everything else. Two details matter. method="json_schema" is Article 6's fix: without it, ChatAnthropic implements structured output as a forced tool call, which Claude Opus 5.5 and Fable 5.1 reject outright, so this keeps triage working if the model is ever upgraded. And the chain is built by build_triage rather than at import time, for the same reason as make_search_docs: the model, and the network calls it implies, are the caller's choice. main.py runs triage first on every incoming message and flags anything high-priority for a human, before the agent handles the reply.

assistant.py: Articles 13 and 14

python
from langchain.agents import create_agent
from langchain.agents.middleware import ModelCallLimitMiddleware, SummarizationMiddleware
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.retrievers import BaseRetriever
from langgraph.checkpoint.memory import InMemorySaver

from knowledge_base import build_retriever
from models import get_model
from tools import check_subscription_status, make_search_docs

SYSTEM_PROMPT = (
    "You are a helpful assistant for Tidewave. Use search_docs for "
    "questions about features, plans, or policies. Use "
    "check_subscription_status for questions about a specific "
    "customer's account; ask for their email if you don't have it."
)


def build_assistant(
    model: BaseChatModel | None = None,
    retriever: BaseRetriever | None = None,
    checkpointer=None,
):
    model = model or get_model()
    tools = [make_search_docs(retriever or build_retriever()), check_subscription_status]
    return create_agent(
        model,
        tools=tools,
        system_prompt=SYSTEM_PROMPT,
        middleware=[
            ModelCallLimitMiddleware(run_limit=6),
            SummarizationMiddleware(model=model, trigger=("messages", 40), keep=("messages", 20)),
        ],
        checkpointer=checkpointer or InMemorySaver(),
        name="tidewave_assistant",
    )

create_agent from Article 13, with two tools instead of one and InMemorySaver providing the checkpointer-based memory Article 8 pointed toward. The rest comes straight from Article 13's middleware section:

  • ModelCallLimitMiddleware(run_limit=6) caps each invoke() at six model calls. A normal answer here takes two or three, so this only fires when something has gone wrong, a model stuck re-calling a tool, instead of leaving LangGraph's roughly 10,000-step default as the only stop.
  • SummarizationMiddleware is Article 8's history-growth problem, solved the agent way. Once a thread passes 40 messages, older ones are condensed into a summary by the same model and the most recent 20 are kept as they are. Tested with the thresholds turned down to 6 and 4: after a few turns, each thread's history stayed at six messages instead of growing, a summary message first.
  • name="tidewave_assistant" is Article 14's detail: it names the root of every trace, so these runs are easy to find in LangSmith.

The system prompt is the one piece of writing in the project that isn't lifted from an earlier article, and it earns its place: with two tools, the model benefits from being told what each is for, the same lesson Article 12 made about a tool's docstring, applied to the assistant's own instructions. Its last clause, asking for an email when there isn't one, matters more than it looks, and the section on what this project leaves out comes back to it.

main.py: Article 14, and the entry point

python
import os

from dotenv import load_dotenv

load_dotenv()
os.environ.setdefault("LANGSMITH_TRACING", "true")

from assistant import build_assistant
from knowledge_base import build_retriever
from triage import build_triage


def main() -> None:
    agent = build_assistant(retriever=build_retriever(persist_directory=".chroma"))
    triage = build_triage()
    config = {"configurable": {"thread_id": "customer-sam"}}

    while True:
        user_input = input("You: ").strip()
        if user_input.lower() in ("quit", "exit"):
            break
        if not user_input:
            continue

        classification = triage.invoke({"message": user_input})
        if classification.priority == "high":
            print(f"[escalation] {classification.category}, high priority: {classification.summary}")

        result = agent.invoke(
            {"messages": [{"role": "user", "content": user_input}]},
            config=config,
        )
        print("Assistant:", result["messages"][-1].text)


if __name__ == "__main__":
    main()

os.environ.setdefault("LANGSMITH_TRACING", "true") is the only line in the project dedicated to observability, and Article 14 is why one line is enough: every model call, every tool execution inside agent.invoke(), and triage's own model call all get traced, because all of it is built on Runnable. It sits right after load_dotenv() and before any project import, so tracing is switched on before anything runs, and setdefault means a LANGSMITH_TRACING=false in .env still wins. Expect two traces per message in LangSmith, one for triage and one rooted at tidewave_assistant, since they're two separate invoke() calls.

The reply is printed with .text, not .content, the Article 5 rule: Claude's messages carry thinking blocks, so .content is a list, and printing it would dump raw blocks at the customer. build_retriever(persist_directory=".chroma") is where the saved index comes from. Wrapping everything in main() behind if __name__ == "__main__": means importing main.py, from a test, say, doesn't start an input loop.

Running it for real: the test suite

Two of this project's three services, Anthropic and OpenAI, need real API keys. Proving the seven modules actually connect, not just read like they should, means standing in for exactly three decisions: which tool the agent calls, how triage classifies a message, and what a text's embedding vector is. Those stand-ins live in one file, used only by the tests:

python
"""Stand-ins that let the whole project run with no API keys.

Each one replaces exactly one external decision: which tool to call,
how to classify a message, or what a text's embedding vector is.
Everything else in the project runs unmodified."""
import math
import re
from collections import Counter

from langchain_core.embeddings import Embeddings
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.messages import AIMessage, HumanMessage, ToolMessage
from langchain_core.outputs import ChatGeneration, ChatResult
from langchain_core.runnables import RunnableLambda

from triage import TicketClassification

VOCAB = ["plan", "bill", "refund", "team", "enterprise", "project", "slack"]


class ToyEmbeddings(Embeddings):
    """Article 10's normalized bag-of-words vectorizer."""

    def _vectorize(self, text: str) -> list[float]:
        words = [w.rstrip("s") if w.endswith("s") and len(w) > 3 else w
                 for w in re.findall(r"[a-z]+", text.lower())]
        counts = Counter(words)
        vec = [float(counts.get(term, 0)) for term in VOCAB]
        norm = math.sqrt(sum(x * x for x in vec))
        return [x / norm for x in vec] if norm else vec

    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        return [self._vectorize(t) for t in texts]

    def embed_query(self, text: str) -> list[float]:
        return self._vectorize(text)


class FakeAssistantModel(BaseChatModel):
    """Picks a tool by keyword in the latest question, then answers with
    the tool's result. A real model reasons about which tool to call;
    this picks deterministically so the run is reproducible. Only the
    most recent message is checked for a tool result, so a stale one
    from an earlier turn in the same thread isn't mistaken for a fresh
    answer."""

    def _generate(self, messages, stop=None, run_manager=None, **kwargs) -> ChatResult:
        if isinstance(messages[-1], ToolMessage):
            message = AIMessage(content=f"Here's what I found: {messages[-1].content}")
            return ChatResult(generations=[ChatGeneration(message=message)])

        turn = sum(isinstance(m, HumanMessage) for m in messages)
        question = next(m.content for m in reversed(messages) if isinstance(m, HumanMessage))
        if "subscription" in question.lower() or "status" in question.lower():
            name, args = "check_subscription_status", {"customer_email": "sam@example.com"}
        else:
            name, args = "search_docs", {"query": question}
        tool_call = {"name": name, "args": args, "id": f"call_{turn}", "type": "tool_call"}
        return ChatResult(generations=[ChatGeneration(message=AIMessage(content="", tool_calls=[tool_call]))])

    def bind_tools(self, tools, **kwargs):
        return self

    @property
    def _llm_type(self) -> str:
        return "fake-assistant-model"


def _classify(prompt_value) -> TicketClassification:
    message = prompt_value.to_messages()[-1].content.lower()
    urgent = any(w in message for w in ("asap", "immediately", "urgent"))
    is_billing = any(w in message for w in ("charge", "refund", "billing", "payment"))
    return TicketClassification(
        category="billing" if is_billing else "other",
        priority="high" if (urgent and is_billing) else "low",
        summary=message[:60],
    )


class FakeTriageModel(BaseChatModel):
    """Keyword matching in place of a real model reading the message."""

    def _generate(self, messages, stop=None, run_manager=None, **kwargs) -> ChatResult:
        raise NotImplementedError("only used through with_structured_output")

    def with_structured_output(self, schema, **kwargs):
        return RunnableLambda(_classify)

    @property
    def _llm_type(self) -> str:
        return "fake-triage-model"

ToyEmbeddings is Article 10's normalized toy vectorizer, FakeAssistantModel is Article 13's FakeAgentModel grown to route between two tools, and FakeTriageModel returns a keyword-matching classifier from with_structured_output, the one method build_triage calls on it. FakeAssistantModel gives each turn's tool call its own id, call_1, call_2, since ids should be unique within a thread. The tests import everything else from the real, unmodified modules:

def test_retriever_finds_refund_policy(retriever):

def test_agent_routes_and_remembers(retriever):
    agent = build_assistant(model=FakeAssistantModel(), retriever=retriever)
    config = {"configurable": {"thread_id": "customer-sam"}}
    first = agent.invoke({"messages": [{"role": "user", "content": "How do refunds work?"}]}, config=config)
    second = agent.invoke({"messages": [{"role": "user", "content": "What's my subscription status?"}]}, config=config)

    tools_called = [m.name for m in second["messages"] if m.type == "tool"]
    assert tools_called == ["search_docs", "check_subscription_status"]
    assert len(second["messages"]) == 8
    assert "Team plan" in second["messages"][-1].text

The two skipped tests are the live half of the suite. Set ANTHROPIC_API_KEY and they run. They're a small, honest start on the evaluation idea from Article 14: fixed inputs, checked against expected behavior, run every time a prompt or model changes. A real evaluation set would have dozens of questions and live in LangSmith, but the idea is the same.

What one message actually costs

The tests prove the pieces connect. To check that main.py makes the right calls against real provider APIs, it was also run end to end against stand-ins that accept or reject requests by each provider's documented September 2026 rules: Claude Sonnet 5, which rejects sampling parameters and requires its thinking blocks to be sent back unmodified during tool use; GPT-5.5; and Gemini 3.8 Flash. The CLI completed both turns on all three, switching providers through nothing but get_model()'s argument. The calls it made, in order, on first start with Claude:

output

anthropic: triage, structured output
anthropic: tool request -> search_docs
openai: embeddings (the search query)
anthropic: final answer
anthropic: triage, structured output
anthropic: tool request -> check_subscription_status
anthropic: final answer
Fig. 2. One message, two independent paths: triage flags it for a human while the agent answers it, neither one blocking the other.

Cost note

Worth reading as a bill. Every customer message costs three model calls, one for triage and two for the agent's request-then-answer loop, plus an embedding call whenever the agent searches the docs. The startup embedding of every chunk happens once: on a second start, with .chroma already on disk, that first line disappeared. And triage is an entire model call spent on classification, so it's the natural first place to use a cheaper, faster model: build_triage(get_model("anthropic:claude-haiku-4-5")).

What this deliberately leaves out

A few things a production support assistant needs aren't in this project, worth naming rather than pretending they're covered:

  • Who the customer actually is. check_subscription_status looks up whatever email appears in the conversation, so anyone could type Sam's email and read Sam's account. In a real deployment, the customer's identity comes from your login system, and the tool looks up the signed-in account rather than trusting an email the model extracted from a chat message. That's also why the system prompt asks for an email instead of guessing: it keeps the demo honest, but it isn't authentication.
  • Memory that survives a restart. InMemorySaver loses every thread when the process exits. Article 13's SqliteSaver or PostgresSaver is a constructor change in build_assistant.
  • A human in the loop. Triage flags urgent billing messages, but nothing stops the agent from answering them anyway. HumanInTheLoopMiddleware (Article 13) could pause those runs for a person to approve.
  • Raw provider SDKs (Articles 2 through 4): api.openai.com and api.anthropic.com appear nowhere in this project, and there are no manually managed message lists or hand-checked parameter ranges. That absence is the payoff of starting below the framework: everything those articles taught by hand is what get_model() and create_agent do underneath.

The whole arc, looking back

Article 1 opened with a claim worth checking against everything above: a framework's abstractions only really make sense once you've felt the problem they solve yourself. get_model() is one line because Articles 2 through 5 made you feel three SDKs disagree first. search_docs is a few lines because Articles 10 and 11 made you debug a vector store's wrong answer by hand first. assistant.py fits on one screen because Article 12 made you write the tool-calling loop yourself before create_agent was allowed to run it for you. Every short module in this project is short for a specific, earned reason, not because the underlying problem was ever simple.

That's the series. Tidewave's assistant is a small project, deliberately, but every line in it does a job you watched get built, one article at a time, and the test suite means you can change any of it and know within seconds whether it still works.
