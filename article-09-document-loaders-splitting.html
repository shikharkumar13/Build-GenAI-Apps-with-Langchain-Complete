Articles 5 through 8 gave Tidewave's assistant a model, reusable prompts, composable chains, and a memory of the conversation. What it still doesn't have is any knowledge of Tidewave itself: ask it about refund policy and it can only guess. Two articles from here, it will answer questions using its actual documentation instead of only what the underlying model already knows. That's retrieval, and it needs two things to exist before any of the retrieval machinery itself makes sense: real documents loaded into a shape LangChain can work with, and those documents broken into pieces small enough to be useful. This article is those two things. Nothing here talks to a model at all, it's entirely about getting real-world data ready.

The Document object

Everything downstream, loaders, splitters, retrievers, later in this series, works with one simple object:

python
from langchain_core.documents import Document

doc = Document(
    page_content="Tidewave offers three plans: Starter, Team, and Enterprise.",
    metadata={"source": "billing.md"},
)

Two fields that matter. page_content is the actual text. metadata is a plain dict for anything else worth remembering about where that text came from, a file path, a page number, a URL, whatever helps later. (There's also an optional id, which you can leave unset; vector stores use it later to identify stored chunks.) A "loader," whatever form it takes, has exactly one job: turn some real file or source into a list of these.

A flag worth reading before you install anything

If you go searching for how to load documents into LangChain, essentially every tutorial you'll find points at langchain-community, a package that has hosted loaders for text files, PDFs, web pages, and dozens of other formats for years.

Sunset notice

That package has now been officially sunset: LangChain announced it on May 22, 2026, and archived the repository, making it read-only, on June 19, 2026. It still installs, imports, and runs, and everything in this section was tested against it, but importing it now prints a DeprecationWarning saying langchain-community "is being sunset and is no longer actively maintained." It receives no further updates or fixes, which matters for a dependency you'd be building production code on. LangChain's recommended migration path is dedicated, standalone integration packages, one per provider or tool, each with its own clear ownership.

This changes the practical advice for this article more than a typical version bump would. For genuinely complex formats, covered further below, a real library is still worth reaching for. But for the simple case, plain text and markdown files, arguably the most common case for something like Tidewave's own documentation, the advice changes more directly: you often don't need a loader package at all.

Loading text without a loader

A Document is two fields. Building one from a text file is a few lines of plain Python, with zero dependency on an archived package:

python
import pathlib
from langchain_core.documents import Document

def load_text_file(path: str) -> Document:
    text = pathlib.Path(path).read_text(encoding="utf-8")
    return Document(page_content=text, metadata={"source": path})

def load_directory(dir_path: str, pattern: str = "*.md") -> list[Document]:
    return [load_text_file(str(p)) for p in sorted(pathlib.Path(dir_path).glob(pattern))]

Run against a real folder of Tidewave's documentation, three markdown files, getting-started, billing, and integrations:

python
docs = load_directory("tidewave_docs")
print(f"Loaded {len(docs)} documents")
for d in docs:
    print(f"  {d.metadata['source']} -> {len(d.page_content)} chars")

Genuine output from actually running this:

output
Loaded 3 documents
  tidewave_docs/billing.md -> 1057 chars
  tidewave_docs/getting-started.md -> 1028 chars
  tidewave_docs/integrations.md -> 688 chars
Fig. 1 — Simple formats are cheap enough to load by hand; genuinely complex ones are where a real library still earns its place.

load_directory here is doing everything langchain-community's DirectoryLoader would have done for this case, glob a folder, load each match, return a list of Documents, in about four lines, actively maintained by nobody but you, which for something this small is exactly the point.

When a real loader still earns its place

Plain text has no structure worth parsing. PDFs do, fonts, layout, page boundaries, sometimes embedded images and tables, and writing a correct PDF parser from scratch is genuinely hard. This is where reaching for a library instead of rolling your own stops being a style preference and starts being the right call.

The library doing the actual work, even inside langchain-community's now-archived PyPDFLoader, is pypdf, a separate, actively maintained package with no connection to the sunset. Using it directly, wrapped into Document objects the same way as before:

python
import pypdf
from langchain_core.documents import Document

reader = pypdf.PdfReader("tidewave_docs/enterprise-sla.pdf")
pdf_docs = [
    Document(
        page_content=page.extract_text(),
        metadata={"source": "tidewave_docs/enterprise-sla.pdf", "page": i},
    )
    for i, page in enumerate(reader.pages)
]

print(pdf_docs[0].metadata)
print("->", repr(pdf_docs[0].page_content[:100] + "..."))

Real output, one page in this example:

output
{'source': 'tidewave_docs/enterprise-sla.pdf', 'page': 0}
-> 'Tidewave Enterprise SLA\nTidewave guarantees 99.9% uptime for Enterprise plan customers,\nmeasured mon...'

langchain-community's PyPDFLoader still works today and does the same thing with less code, plus it fills in extra metadata automatically, PDF producer, creation date, total page count, page label, that you'd otherwise have to pull out yourself:

python
from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("tidewave_docs/enterprise-sla.pdf")
pdf_docs = loader.load()

There's a third option, and it's the one the sunset points toward: a dedicated, standalone loader package. LangChain's document-loader integrations page now lists several for PDFs, among them langchain-pymupdf4llm, langchain-docling, and langchain-unstructured, each maintained by its own team rather than inside the archived monorepo, and several go well beyond plain text extraction into layout, tables, and markdown output.

So this isn't an old-way-versus-new-way situation like Article 6's PydanticOutputParser or Article 8's memory classes; it's a real trade-off between three reasonable choices. pypdf directly for the fewest dependencies, at the cost of a few more lines and any metadata you'd fill in yourself. A standalone loader package for the richest parsing on complex documents, at the cost of a heavier dependency. PyPDFLoader for the least code on a simple PDF today, at the cost of depending on a package that gets no further updates, which makes it the one to avoid for anything you're building to last.

Web pages follow the identical pattern, worth knowing exists without a full example here: fetch the HTML yourself with requests and parse it with BeautifulSoup, reach for a standalone web loader package from the same integrations page, or use langchain-community's WebBaseLoader, which does the requests-plus-BeautifulSoup work internally and inherits the same sunset caveat as PyPDFLoader.

Why splitting matters at all

Article 1's second point about LLMs, no knowledge of your private data, is the reason retrieval exists in the first place. But you don't hand a model your entire documentation folder on every question; you find the relevant few paragraphs and hand it those. Finding "the relevant few paragraphs" means having paragraphs to search over in the first place, not whole documents. A 1,000-word doc treated as one unit means a question about refund policy pulls in the entire billing page, integrations and all, when only two sentences were actually relevant. Split too small, on the other hand, and you lose surrounding context a chunk needed to make sense on its own. Article 11 covers retrieval itself; this article's job is just producing chunks worth retrieving.

RecursiveCharacterTextSplitter

Unlike the loaders above, this one lives in langchain-text-splitters, a healthy, separately maintained package with no connection to the sunset, worth being precise about since it's easy to lump every LangChain sub-package into the same worry once you've seen one get archived.

python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,
    chunk_overlap=50,
)

chunks = splitter.split_documents(docs)
print(f"{len(docs)} documents split into {len(chunks)} chunks")

Real output, splitting the three Tidewave markdown files from earlier:

output
3 documents split into 12 chunks

"Recursive" describes the actual splitting strategy: it tries to break on double newlines (paragraph boundaries) first, and only falls back to single newlines, then spaces (so, between words), and finally individual characters, if a piece is still too big after that. Those four separators, ["\n\n", "\n", " ", ""], are its defaults; note that there's no sentence-level step, so in prose without line breaks it goes straight from paragraphs to words. In practice, on real markdown, this means it naturally tends to split along your document's own structure rather than slicing mid-sentence. Two genuine chunks from running the code above, back to back:

output
--- chunk 1 (296 chars) ---
## Plan pricing

The Starter plan is free for up to 3 team members. The Team plan is billed
per seat, per month, and includes unlimited projects, integrations, and
priority support. Enterprise pricing is custom and includes SSO, audit
logs, and a dedicated account manager.

## Changing your plan

--- chunk 2 (217 chars) ---
## Changing your plan

Workspace admins can upgrade or downgrade a plan at any time from
Settings > Billing. Upgrades take effect immediately; downgrades take
effect at the start of the next billing cycle.

## Refunds
Fig. 2 — Real output: "## Changing your plan" appears at the tail of chunk 1 and the head of chunk 2, the actual overlap in action.

Notice ## Changing your plan appears at the end of chunk 1 and again at the start of chunk 2, that's chunk_overlap=50 doing its job: carrying a little of the previous chunk's tail, up to 50 characters, into the next one, so a heading (or the last sentence before it) doesn't get orphaned from the section it introduces. Rerun the same split with chunk_overlap=0 and you can see the problem it's solving: the heading still lands at the end of chunk 1, but chunk 2 now begins "Workspace admins can upgrade or downgrade a plan..." with no heading at all. chunk_size=300 is a maximum, not a target: no chunk will exceed 300 characters (the character-level fallback guarantees it), but most come in under it, because the splitter prefers ending on a paragraph or line boundary over filling the chunk to the brim. There's no universal correct value for either parameter, it depends on your content and, eventually, how your retrieval performs in Article 11; 300 to 1,000 characters with 10-20% overlap is a reasonable starting range for prose documentation like Tidewave's.

One more thing worth knowing exists without a full detour: format-aware splitters. MarkdownHeaderTextSplitter, for instance, splits strictly on heading levels and attaches the heading path itself as metadata on each chunk, worth reaching for specifically if you already know your source is consistently structured markdown and want that structure preserved as searchable metadata rather than just influencing where the cuts happen.

What's next

Chunks of text aren't searchable by meaning yet, they're just shorter strings. Next up: embeddings, turning each chunk into a vector that captures what it's actually about, and a vector store to hold them in, the two pieces that make "find the relevant paragraphs" an operation you can actually run instead of something you do by hand.
