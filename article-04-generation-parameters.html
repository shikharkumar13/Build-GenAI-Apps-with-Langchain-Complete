A one-paragraph refresher on why any of this works

Article 1 covered the mechanic underneath every LLM call: given the tokens so far, the model produces a probability distribution over what token comes next, something gets sampled from that distribution, and the process repeats. Every parameter in this article is a knob on that sampling step, not on the model's underlying "knowledge." Temperature, top-p, and top-k all reshape the same distribution before a token gets picked from it. Keep that picture in mind; it's what makes the rest of this article predictable instead of a list of settings to memorize.

Temperature

Temperature controls how sharply the model favors its highest-probability tokens versus giving lower-probability ones a real chance. Low temperature squeezes the distribution toward the single most likely token, so outputs are consistent and repeatable. High temperature flattens it, so less likely tokens get picked more often, which reads as creativity right up until it reads as nonsense.

Fig. 1 — Temperature doesn't change what the model knows, only how sharply it favors its own top guess before a token gets sampled.

The range is not the same across providers:

ProviderRangeDefault
OpenAI0.0 – 2.01.0
Anthropic0.0 – 1.01.0
Gemini0.0 – 2.01.0

A temperature of 1.5 is a legitimate, if unusual, setting on OpenAI or Gemini. Send the exact same value to Anthropic and it's out of range. If you're writing code that might run against more than one provider (which, after the last two articles, you probably are), don't treat "temperature" as one universal number, check the range for whoever you're actually calling.

But the range isn't the most important fact in this article any more. This is: on the newest reasoning models, you often can't set temperature at all. These models do hidden reasoning before they answer, their providers tune the sampling for that themselves, and they increasingly refuse to let you override it:

  • OpenAI: gpt-5.5 rejects any temperature other than the default 1 with a 400 error (Unsupported value: 'temperature' does not support 0 with this model), unless you turn its reasoning off with reasoning_effort="none". OpenAI's docs say it plainly: when reasoning effort isn't none, remove temperature, top_p, and logprobs.
  • Anthropic: claude-sonnet-5 returns a 400 error for any non-default temperature, top_p, or top_k, with no switch to turn them back on. Anthropic's advice is to steer behavior through the system prompt instead. Anthropic introduced the same restriction earlier on Claude Opus 4.7; the smaller claude-haiku-4-5-20251001 still accepts the classic knobs. The Python SDK has followed suit: since version 1.0 (August 2026), client.messages.create() no longer has temperature, top_p, or top_k arguments at all, so passing one raises a TypeError before any request is even sent. On a model that still accepts them, you pass them through extra_body instead, which the last example in this article shows.
  • Gemini: still accepts a temperature, but that's where the next gotcha comes in.

Gemini's version of the gotcha is quieter: Google's own documentation now recommends leaving Gemini 3 models at their default temperature of 1.0 rather than lowering it for more deterministic output, the way you'd instinctively do on the other two providers. Gemini 3's reasoning is tuned for that default, and dropping the temperature can actually cause repetition loops or degraded performance on complex tasks, the opposite of what lowering temperature is supposed to buy you. It's a genuine reversal of the "lower temperature equals more reliable" intuition this article is about to build, and it only applies to Gemini's newest reasoning models, so it's worth rechecking Google's docs before assuming the classic advice still holds for whichever Gemini model you're on.

One more thing worth internalizing before you touch code: even at temperature 0, output isn't perfectly guaranteed to be identical run to run. Floating-point arithmetic on the hardware serving the request introduces tiny variations that can occasionally tip a near-tied probability one way or the other. Temperature 0 buys you overwhelming consistency, not a cryptographic guarantee. That's a direct echo of Article 1's point about LLMs being non-deterministic; parameters can shrink that non-determinism, not eliminate it.

Try it yourself: the actual experiment worth running

The clearest way to build intuition for temperature is to watch it change the same prompt in front of you, not read about it:

python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

prompt = "Write a two-sentence story about a lighthouse keeper."

for temp in [0.0, 0.3, 0.7, 1.0, 1.5]:
    response = client.chat.completions.create(
        model="gpt-5.5",
        messages=[{"role": "user", "content": prompt}],
        reasoning_effort="none",
        temperature=temp,
    )
    print(f"\n--- temperature={temp} ---")
    print(response.choices[0].message.content)

Notice reasoning_effort="none". Without it, the very first iteration fails with the 400 error from above, because gpt-5.5 reasons at medium effort by default and won't take a custom temperature while it does. Switching reasoning off turns it back into a classic sampler, which is exactly what this experiment needs.

Run that once. The pattern to expect: 0.0 and 0.3 will produce very similar, fairly plain versions of the story, sometimes word-for-word identical between runs. By 0.7 you'll see real variation in phrasing and imagery while the story stays coherent. At 1.0 the outputs diverge more noticeably from each other. By 1.5 you're likely to see occasional weird word choices or shaky grammar creeping in, the model reaching further into its tail of unlikely-but-not-impossible tokens.

Then run the same loop with a factual prompt instead, something like "What year did the Berlin Wall fall?". You'll very likely get 1989 at every temperature, and that's instructive in its own way: the model's distribution for that answer is so sharply peaked that there's almost nothing else to sample, and temperature only matters where the model has real alternatives. Ask something it's less sure of, a niche date or an obscure statistic, and higher temperatures are exactly how wrong answers creep in, not because the model "forgot," but because the mechanism doesn't distinguish between "creative" and "wrong": it just samples further from the peak of the distribution, and for a factual question, everything that isn't the peak is an error. This is the concrete reason low temperature is the classic default for anything with one correct answer, and higher temperature belongs to tasks where variety itself is the goal.

Top-p (nucleus sampling)

Top-p works differently: instead of reshaping the whole distribution like temperature, it truncates it. The model ranks tokens by probability, adds them up starting from the most likely, and only samples from the smallest set of tokens whose cumulative probability crosses the top-p threshold. top_p=0.9 means "only consider tokens from the most-likely group that together account for 90% of the probability mass," discarding the long, unlikely tail entirely before any randomness gets applied.

Fig. 2 — top_p=0.9 keeps only the highest-ranked tokens whose probabilities sum to 90%, then samples (with temperature) from just that shortened list.

The practical effect overlaps with temperature (both increase or decrease output variety), which is why providers recommend adjusting temperature or top-p for a given call, not both at once. Anthropic has gone further and enforces it: on current Claude models that still accept sampling parameters, such as Haiku 4.5, sending both returns an error saying temperature and top_p cannot both be specified. Stacking them makes the actual effect harder to reason about and doesn't buy you anything a single knob can't.

python
response = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user", "content": prompt}],
    reasoning_effort="none",
    top_p=0.9,
    # temperature left at its default when top_p is the one being tuned
)

Where it's accepted, top_p means the same 0.0–1.0 thing on all three providers, so unlike temperature's range it's genuinely consistent. The lockdown from the temperature section applies here too, though: gpt-5.5 only takes it with reasoning off, and claude-sonnet-5 doesn't take it at all.

Top-k, briefly

Top-k is a blunter cousin of top-p: instead of a cumulative probability threshold, it just keeps the k most likely tokens and discards the rest before sampling. top_k=1 is equivalent to always picking the single most likely token (greedy decoding, effectively temperature 0). Anthropic and Gemini both expose top_k (on Anthropic, only on models that still accept sampling parameters, so not claude-sonnet-5); OpenAI's Chat Completions API doesn't offer it at all. Anthropic's own guidance is blunt about this one: it's recommended for advanced use cases only, and most applications get everything they need from temperature or top-p alone. Worth knowing it exists; not worth reaching for by default.

Reasoning effort and thinking

This is the knob Article 2 promised: how much a model reasons internally before writing its actual answer. On current models it's arguably more important than temperature, and it's a genuinely different kind of knob than everything above. Instead of shaping how one response gets sampled, it controls how much hidden reasoning happens before the answer is written at all. All three providers now think by default on their current models, and all three let you dial it:

  • OpenAI: reasoning_effort, a qualitative string. On gpt-5.5 the options are "none", "low", "medium" (the default), "high", and "xhigh"; other models support a slightly different set, which can include "minimal" and "max".
  • Anthropic: on claude-sonnet-5, thinking is adaptive, meaning the model decides how much to think per request, and you steer its depth with output_config={"effort": ...}, one of "low", "medium", "high" (Sonnet 5's default), "xhigh", or "max". thinking={"type": "disabled"} turns it off. The older form you'll see in many tutorials, thinking={"type": "enabled", "budget_tokens": 1024}, an explicit reasoning-token budget, now returns a 400 error on Claude 4.7 and later models; it still works on claude-haiku-4-5-20251001, which uses that manual style instead of adaptive thinking.
  • Gemini: Gemini 3 models use thinking_level inside thinking_config; on gemini-3.8-flash that's "low", "medium" (the default), or "high", and thinking can't be switched off entirely on that model. Older tutorials written for Gemini 2.5 set a numeric thinking_budget instead.

Here's what dialing it down looks like on the two providers you haven't set it on yet:

python
from anthropic import Anthropic
from google import genai
from google.genai import types

claude = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))
gemini = genai.Client(api_key=os.getenv("GOOGLE_API_KEY"))

response = claude.messages.create(
    model="claude-sonnet-5",
    max_tokens=4096,
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": prompt}],
)
print("".join(block.text for block in response.content if block.type == "text"))

response = gemini.models.generate_content(
    model="gemini-3.8-flash",
    contents=prompt,
    config=types.GenerateContentConfig(
        thinking_config=types.ThinkingConfig(thinking_level="low"),
    ),
)
print(response.text)

Three providers, three different shapes, same pattern as everything else in this article. The trade-off is the same everywhere, though: more reasoning generally means better answers on hard, multi-step problems, and more latency and cost on every call, since hidden reasoning tokens are billed as output tokens. For a two-sentence story, low effort is plenty. For a tricky refactor, it's worth paying for more.

Max output tokens

Every provider lets you cap how much a model is allowed to generate, both to control cost (you pay per output token) and to stop a model from rambling well past a useful answer. The parameter name is where the differences pile up:

  • OpenAI: max_completion_tokens is the current parameter. There's an older max_tokens, still accepted on some models for backward compatibility, but it's deprecated and doesn't work at all on OpenAI's reasoning-model tiers. Use max_completion_tokens in new code.
  • Anthropic: max_tokens, and as you saw in Article 2, it's required, not optional. Every Anthropic call needs one.
  • Gemini: max_output_tokens, set inside the same GenerateContentConfig object you saw in Article 3.

One thing changes the maths on current models: the cap covers hidden reasoning as well as the visible answer. OpenAI's cap counts reasoning tokens, and Anthropic's docs state that thinking tokens count toward max_tokens. On gpt-5.5 at its default effort, a tight cap like 300 can be used up entirely by reasoning, leaving you an empty reply that stopped with finish_reason set to "length". So either give reasoning room, or, when you genuinely want a short, capped answer, turn reasoning down, as here:

python
# OpenAI
response = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user", "content": prompt}],
    reasoning_effort="none",
    max_completion_tokens=300,
)

A capped response doesn't get shortened gracefully, it gets cut off mid-thought the instant the cap is hit. If you're capping tokens for cost control on something like a paragraph-length answer, leave enough headroom that a normal response actually finishes; treat the cap as a safety ceiling against runaway generation, not a target length.

Stop sequences

A stop sequence tells the model to halt generation the moment it produces a specific string, without including that string in the output. This is genuinely useful when you're generating something with a predictable delimiter, list items separated by a marker you control, or a structured format where you know exactly what token should signal "done."

  • OpenAI: stop, a string or a list of up to a few strings, but only on OpenAI's older, non-reasoning chat models. The GPT-5 family, gpt-5.5 included, rejects it with Unsupported parameter: 'stop' is not supported with this model.
  • Anthropic: stop_sequences, a list, and still supported on current models, claude-sonnet-5 included.
  • Gemini: stop_sequences, inside GenerateContentConfig.

Since gpt-5.5 won't take one, here it is on Claude:

python
response = claude.messages.create(
    model="claude-sonnet-5",
    max_tokens=4096,
    stop_sequences=["DONE"],
    messages=[{"role": "user", "content": "List three colors, one per line, then write DONE."}],
)
print("".join(block.text for block in response.content if block.type == "text"))
print(response.stop_reason, response.stop_sequence)

The last line is worth running once: stop_reason comes back as "stop_sequence" and stop_sequence as "DONE", which is how your code can tell a deliberate stop apart from the model simply finishing ("end_turn") or hitting the cap ("max_tokens").

Presence and frequency penalty

These two reduce repetition, but in different ways. Frequency penalty scales down a token's probability in proportion to how many times it's already appeared in the output so far, so a word used five times gets suppressed harder than a word used once. Presence penalty is blunter: any token that has appeared at all gets a flat penalty, regardless of how many times. Frequency penalty fights "the model keeps reusing the same phrase over and over"; presence penalty pushes the model toward covering new topics instead of circling the same ones.

This is the parameter set with the least support left anywhere. OpenAI's GPT-5 family, gpt-5.5 included, doesn't accept either penalty; they only work on OpenAI's older, non-reasoning chat models. Anthropic has never offered either one. And Gemini's config has fields for both, but Google hasn't enabled them on every model: the Gemini 2.5 models, for example, reject them with Penalty is not enabled for models/.... So if a model keeps looping on the same phrase, don't reach for a penalty first. A stop sequence, a clearer prompt, or a fresh call is the fix that ports everywhere.

Read that table column by column and a pattern jumps out: on each provider's current mainstream model, the parameters that still work everywhere are the reasoning dial and the output cap. The classic sampling knobs survive mainly on older or smaller models and on reasoning-off modes. Put together, one call using several of these at once looks like this on OpenAI:

python
response = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user", "content": prompt}],
    reasoning_effort="none",
    temperature=0.7,
    max_completion_tokens=300,
)

The Anthropic equivalent on claude-sonnet-5 swaps the sampling knobs for the effort dial and a stop sequence:

python
response = claude.messages.create(
    model="claude-sonnet-5",
    max_tokens=2048,
    output_config={"effort": "low"},
    stop_sequences=["DONE"],
    messages=[{"role": "user", "content": prompt}],
)

And if you specifically need classic sampling on Claude, drop to the smaller model that still accepts it, and pass the knob through extra_body, since the 1.x SDK no longer has a temperature argument. Set temperature or top-p, not both:

python
response = claude.messages.create(
    model="claude-haiku-4-5-20251001",
    max_tokens=300,
    stop_sequences=["DONE"],
    extra_body={"temperature": 0.7},
    messages=[{"role": "user", "content": prompt}],
)

extra_body merges extra fields into the JSON request the SDK sends, which is the general escape hatch for any parameter the API accepts but the SDK doesn't declare. Send the same extra_body to claude-sonnet-5 and you're back to the 400 error from the temperature section: the SDK lets it through, the model still refuses it.
