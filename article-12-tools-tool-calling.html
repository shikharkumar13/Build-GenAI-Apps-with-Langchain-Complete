Tidewave's assistant can now answer from real documentation, Article 11 covered that. What it still can't do is anything specific to one customer: it can describe the refund policy in general, but it can't tell Sam what Sam's own subscription status actually is right now. That's not a documentation problem, no amount of retrieval fixes it, it's a different capability entirely: letting the model trigger real code and use the result. That's what a tool is.

The idea, and where you've already seen half of it

Article 6 introduced with_structured_output, and it's a close cousin of what this article covers. There, the model's output was bound to one schema, TicketClassification, and LangChain turned the result into a real object for you. Article 6 even mentioned that ChatAnthropic's default way of doing that is a forced tool call, a tool whose arguments are the schema, before switching to the native json_schema method. Tool calling is the general version of that idea. Instead of one fixed schema the model always fills in, you give it several tools, each with its own schema, and the model decides which one (if any) to call and what arguments to call it with. The model never runs your code. It asks; your code decides whether and how to actually do it.

Defining a tool

python
from langchain_core.tools import tool

@tool
def check_subscription_status(customer_email: str) -> str:
    """Check a Tidewave customer's current subscription plan and billing status."""
    fake_db = {
        "sam@example.com": "Team plan, active, next billing date 2026-09-15",
        "priya@example.com": "Starter plan, active",
    }
    return fake_db.get(customer_email, "No account found for that email.")

The @tool decorator turns an ordinary Python function into something a model can be offered. Two things it pulls directly from the function itself, both genuinely sent to the model, not just documentation for you:

  • The docstring becomes the tool's description. This is exactly the same point Article 6 made about Field(description=...), it's the text the model actually reads to decide when this tool is the right one to reach for. A vague docstring produces a model that reaches for the tool at the wrong times, or not at all.
  • The type-hinted parameters become the argument schema, customer_email: str here, the same way a Pydantic model's fields did in Article 6. The model has to produce arguments matching this shape.

check_subscription_status here uses a hardcoded dictionary standing in for Tidewave's real customer database, obviously not production code, but it's the right level of detail for seeing the mechanism clearly: a tool is just a function, wrapped so a model can request it.

Binding tools to a model

python
from models import get_model

model = get_model()
model_with_tools = model.bind_tools([check_subscription_status])

get_model() is Article 5's project helper, unchanged, the same one every article since has reached for. bind_tools doesn't change what model does with a plain question, it adds the option. Call .invoke() on the result the same way as always; the model now has the tool's schema available and can choose to use it.

What actually comes back: a request, not a result

This is the part worth being precise about, since it's easy to assume calling the model with tools bound somehow runs the tool automatically. It doesn't.

python
response = model_with_tools.invoke("What's my subscription status? My email is sam@example.com")
print(response.tool_calls)

If the model decides to use the tool, response.tool_calls holds a list like this:

python
[{
    "name": "check_subscription_status",
    "args": {"customer_email": "sam@example.com"},
    "id": "toolu_01A9...",
    "type": "tool_call",
}]

A name, a dict of arguments matching the schema, and an id, generated by the provider: Claude's look like toolu_01..., OpenAI's like call_..., and for Gemini LangChain assigns one itself. That's a request. Don't rely on response.content to tell you a tool was requested, either: with OpenAI and Gemini it usually comes back empty, but Claude often says something first ("Let me check that for you."), and with its thinking on by default, Claude's .content is a list holding a thinking block, that text, and the tool request. response.tool_calls is the one field that looks the same on every provider. Nothing has actually looked up Sam's subscription yet, that's still your job.

Fig. 1 — Binding a tool offers the model an option to ask for it. It never grants the model the ability to run it.

Running the tool and closing the loop

The part that needs a live model call is deciding whether to use the tool. Everything after that, actually running it and continuing the conversation, needs no API key at all, and is worth executing for real:

python
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage, ToolMessage

messages = [
    SystemMessage(content="You are a helpful assistant for Tidewave."),
    HumanMessage(content="What's my subscription status? My email is sam@example.com"),
]

# In production this next line is: ai_response = model_with_tools.invoke(messages)
# Standing in here with the exact shape a real tool-calling response takes,
# so the rest of this loop can run and be verified for real, same honest
# pattern Articles 8 and 11 used for a live model call.
ai_response = AIMessage(
    content="",
    tool_calls=[{
        "name": "check_subscription_status",
        "args": {"customer_email": "sam@example.com"},
        "id": "call_1",
        "type": "tool_call",
    }],
)
messages.append(ai_response)

for tool_call in ai_response.tool_calls:
    result = check_subscription_status.invoke(tool_call["args"])
    messages.append(ToolMessage(content=result, tool_call_id=tool_call["id"]))

for m in messages:
    print(f"{type(m).__name__} -> {m.content!r}")

Genuine output, printing the message list at this point:

output
SystemMessage -> 'You are a helpful assistant for Tidewave.'
HumanMessage -> "What's my subscription status? My email is sam@example.com"
AIMessage -> ''
ToolMessage -> 'Team plan, active, next billing date 2026-09-15'
Fig. 2 — The model never executes anything itself: it asks, your code runs the real function, then the model gets called again with the result already in hand.

Walking through the loop: check_subscription_status.invoke(tool_call["args"]) actually runs the real function, the tool itself is a Runnable too, same as everything else in this series, and tool_call["args"] is already shaped exactly as the function expects since the model built it against the schema @tool generated. ToolMessage wraps the result with tool_call_id, the same id from the request, so the model can match a result back to the specific call that asked for it, important once more than one tool call is in flight at once. (There's a shortcut worth knowing: pass the whole tool call, check_subscription_status.invoke(tool_call), instead of just its args, and the tool hands back a ready-made ToolMessage with the id already filled in.) Append that ToolMessage to messages and call the model again, model_with_tools.invoke(messages), and this time it has everything it needs: the original question, its own request, and a real answer to that request. It replies in natural language, incorporating Sam's actual subscription status instead of asking about it or making something up.

One rule for the production version of that loop: append the AIMessage the model actually returned, exactly as it came back, never a rebuilt one like the stand-in above. The stand-in is fine for running the loop without a key, but a real response can carry more than the tool request. Anthropic's documentation says that when Claude's thinking accompanies a tool call, those thinking blocks must be passed back complete and unmodified with the tool result, and a modified or missing one is rejected with a 400 error. Gemini's documentation likewise says its thought blocks must be resent exactly as received. Appending the original message object takes care of both, because LangChain keeps all of that inside it.

Why the model doesn't always call a tool

Worth expecting, not worth engineering around: given ["check_subscription_status"] and a message like "What plans do Enterprise customers get?", a well-behaved model won't call the tool at all, it'll just answer from what it already knows, since the question doesn't need any specific customer's data. Binding a tool offers the option; it doesn't force the model to take it. You can force it, bind_tools([...], tool_choice="any") requires some tool call, or name one specific tool, but use that sparingly: it's the same forced tool use that Anthropic's newest top models, Claude Opus 5.5 and Fable 5.1, reject outright, as Article 6 found. This is exactly why Tidewave's assistant, once tools and retrieval both exist, needs to decide per question which capability actually applies, sometimes neither, sometimes both. That decision-making, choosing across multiple tools and multiple turns, is precisely what Article 13 covers next.
